<h2 id="what-is-gitlab">What is GitLab?<a aria-hidden="true" tabindex="-1" href="#what-is-gitlab"><span class="anchor-link"> #</span></a></h2>
<p><strong>GitLab</strong> is a source-code repository management system (an open-source project). It uses Git for version control and ships a web UI. Many teams with relatively simple org structures prefer it as their Git platform.</p>
<h2 id="what-can-it-do">What can it do?<a aria-hidden="true" tabindex="-1" href="#what-can-it-do"><span class="anchor-link"> #</span></a></h2>
<p>As a repository manager, GitLab gives a friendlier UI for managing project code. It can also integrate CI/CD: deploy <strong>GitLab Runner</strong> for continuous integration and delivery.</p>
<p>That is enough for everyday project work.</p>
<blockquote>
<p>Large, complex programs often separate the repository system from CI/CD. Repo tooling varies (homegrown or based on other OSS); CI/CD is often Jenkins, with a richer mature plugin and pipeline ecosystem. GitLab may not fit every such case.</p>
</blockquote>
<h2 id="setup-steps">Setup steps<a aria-hidden="true" tabindex="-1" href="#setup-steps"><span class="anchor-link"> #</span></a></h2>
<p>Here is how I stood up a test instance.</p>
<h3 id="stand-up-the-gitlab-core">Stand up the GitLab core<a aria-hidden="true" tabindex="-1" href="#stand-up-the-gitlab-core"><span class="anchor-link"> #</span></a></h3>
<p>Docker Hub already publishes <strong>GitLab</strong> images, so deploying with Docker is straightforward.</p>
<p><img src="/post/deploygitlabcerunner/530bd021d4e1.png" alt="docker-gitlab-ce"></p>
<p>The image has many tags — pin a version or take the latest.</p>
<p>I deploy the management UI with a <code>docker-compose.yml</code>. When adding the service, set <code>GITLAB_OMNIBUS_CONFIG</code> so startup options are passed into the container.</p>
<p>Once the service is up, open a browser to your self-hosted GitLab:</p>
<p><img src="/post/deploygitlabcerunner/e2e1519d6a0e.png" alt="login"></p>
<h3 id="sign-in-as-admin">Sign in as admin<a aria-hidden="true" tabindex="-1" href="#sign-in-as-admin"><span class="anchor-link"> #</span></a></h3>
<p>Next, sign in as admin to finish configuration. The username is <code>root</code>; the password comes from inside the container. You can also grab the container IP for later settings:</p>
<p><img src="/post/deploygitlabcerunner/9442444b2afa.png" alt="gitlab-ce-info"></p>
<p>Use that password to log in.</p>
<p><img src="/post/deploygitlabcerunner/1c87025556eb.png" alt="admin-dashboard"></p>
<p>After login you land in admin settings, where you can configure the whole repository system.</p>
<blockquote>
<p>We are not building GitLab only as a code host. If you only need a repo, consider something like <code>gogs</code> — fast, simple, and GitHub-like. We want CI/CD as well.</p>
</blockquote>
<h4 id="cicd-environment">CI/CD environment<a aria-hidden="true" tabindex="-1" href="#cicd-environment"><span class="anchor-link"> #</span></a></h4>
<p>This is the main part.</p>
<p>With the above in place, deploy <strong>GitLab Runner</strong> — the CI/CD agent. Under admin, open <strong>Runners</strong> to see the available list:</p>
<p><img src="/post/deploygitlabcerunner/f6e0f2e2f440.png" alt="runners"></p>
<p>It is empty. Normally you install GitLab Runner on a worker machine.</p>
<p>I only wanted to poke at GitLab features, so I kept it simple: run <strong>GitLab Runner</strong> in Docker and register it locally. For IP resolution across containers, I added a hosts entry:</p>
<div class="code-block-wrapper"><div class="code-block-header"><span class="code-block-lang">vbnet</span><button class="copy-button" data-copy-state="copy" aria-label="Copy code to clipboard" type="button" onclick="copyCode(this)"><span class="copy-button-text">Copy</span></button></div><pre><code class="hljs language-vbnet"><span class="hljs-number">192.168</span>.<span class="hljs-number">176.2</span> gitlab.<span class="hljs-keyword">me</span>
</code></pre></div>
<p><code>192.168.176.2</code> may differ on your machine — use the GitLab container’s IP so other containers resolve correctly.</p>
<p>Register the runner (copy the <code>token</code> from <strong>Registration token</strong> in the screenshot above):</p>
<p><img src="/post/deploygitlabcerunner/53a51f2560c9.png" alt="runner-register"></p>
<p>After registration, the runner appears in the Runners list.</p>
<blockquote>
<p>I chose the <code>docker</code> executor so I can build with a Docker image (gcc). That fits a Docker-based deploy. If Runner is installed on a bare machine that already has a toolchain, use the <code>shell</code> executor. If the worker must SSH to another host to build, use <code>ssh</code>. Pick based on your environment.</p>
</blockquote>
<p>After registration, the new runner shows up:</p>
<p><img src="/post/deploygitlabcerunner/d954e9363c1c.png" alt="runner-list"></p>
<p>Click the left-hand link for details:</p>
<p><img src="/post/deploygitlabcerunner/1e90dd45eba5.png" alt="runner-details"></p>
<p>Click the pencil on the right to edit settings:</p>
<p><img src="/post/deploygitlabcerunner/5329eafbdd66.png" alt="runner-enable-untag"></p>
<p>I checked <strong>Run untagged jobs</strong> and saved.</p>
<p>That finishes the basic Runner setup.</p>
<blockquote>
<p>Runners have more options — see the official docs.</p>
</blockquote>
<h3 id="create-a-regular-user">Create a regular user<a aria-hidden="true" tabindex="-1" href="#create-a-regular-user"><span class="anchor-link"> #</span></a></h3>
<p>Open a private window, go to login, click <strong>Register now</strong>, fill in the form, then have an admin approve the user. Once approved, the new user can sign in (the screenshot shows a user who already created a project):</p>
<p><img src="/post/deploygitlabcerunner/279ae5d2774b.png" alt="user-projects"></p>
<p>This account is the developer used for the CI/CD test below.</p>
<h4 id="create-a-project">Create a project<a aria-hidden="true" tabindex="-1" href="#create-a-project"><span class="anchor-link"> #</span></a></h4>
<p>Click <strong>New project</strong> and fill in the basics:</p>
<p><img src="/post/deploygitlabcerunner/e89af7df63df.png" alt="new-project"></p>
<h4 id="set-up-gitlab-ciyml">Set up <code>.gitlab-ci.yml</code><a aria-hidden="true" tabindex="-1" href="#set-up-gitlab-ciyml"><span class="anchor-link"> #</span></a></h4>
<p>Add a <code>.gitlab-ci.yml</code> at the repo root with pipeline jobs.</p>
<p>Mine is minimal: <code>script</code> for the build command, <code>only</code> for the branch (<code>main</code>), and <code>tags</code> matching the runner’s tags.</p>
<blockquote>
<p>More <code>.gitlab-ci.yml</code> detail: <a href="https://docs.gitlab.com/ee/ci/yaml/gitlab_ci_yaml.html">official docs</a>.</p>
</blockquote>
<h4 id="push-code-and-run-ci">Push code and run CI<a aria-hidden="true" tabindex="-1" href="#push-code-and-run-ci"><span class="anchor-link"> #</span></a></h4>
<p>With everything ready, write code and push to <code>main</code>:</p>
<p><img src="/post/deploygitlabcerunner/fc979b40e6df.png" alt="git-push"></p>
<p>Right after the push, the pipeline updates:</p>
<p><img src="/post/deploygitlabcerunner/94be700a77c7.png" alt="pipelines"></p>
<p>Open the running pipeline for job details:</p>
<p><img src="/post/deploygitlabcerunner/121b5fa098bf.png" alt="pipeline-success"></p>
<p>That completes a basic GitLab setup with CI/CD. Overall it is a practical code-management stack.</p>

<h3 id="pitfalls-i-hit">Pitfalls I hit<a aria-hidden="true" tabindex="-1" href="#pitfalls-i-hit"><span class="anchor-link"> #</span></a></h3>
<blockquote>
<p>Likely gotchas:</p>
<ol>
<li>If <code>external_url</code> in <code>GITLAB_OMNIBUS_CONFIG</code> includes a port, Docker’s service listen binds to that port.</li>
<li>In the runner <code>config.toml</code>, under <code>runner.docker</code>, set <code>network_mode</code> to <code>gitlab-network</code> to match <code>docker-compose.yml</code>.</li>
