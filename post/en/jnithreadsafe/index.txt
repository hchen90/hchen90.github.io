16:T3313,<h1 id="what-is-jni-development">What is JNI development?<a aria-hidden="true" tabindex="-1" href="#what-is-jni-development"><span class="anchor-link"> #</span></a></h1>
<p>I used to do this kind of work, and after a former colleague raised some questions, I set aside time to dig into JNI development issues and one specific detail — thread safety of calls. JNI-layer calls are not that different from other languages calling into C/C++ — for example CGO between Go and C/C++ shares many of the same concerns.</p>
<p>JNI is Java’s native interface. With C/C++ (or other languages), compiled code inside the JVM can interact with native code outside it.</p>
<blockquote>
<p>Java emphasizes portability. Native code looks like it breaks that promise, but it is often unavoidable — Java cannot implement every low-level capability.</p>
</blockquote>
<h1 id="what-tools-do-you-need-for-jni">What tools do you need for JNI?<a aria-hidden="true" tabindex="-1" href="#what-tools-do-you-need-for-jni"><span class="anchor-link"> #</span></a></h1>
<p>On my machine I run OpenJDK 11 and GCC 11 on Linux. For editing I use VS Code with the Java, CMake, and C++ extensions.</p>
<p>Toolchain:</p>
<ul>
<li>OpenJDK 11</li>
<li>GCC 11</li>
<li>CMake 3.21</li>
<li>Latest VS Code</li>
</ul>
<p>Screenshot:</p>
<p><img src="/post/jnithreadsafe/8025a99f2589.png" alt="vscode"></p>
<blockquote>
<p>Why can’t OpenJDK find <code>javah</code>? See <a href="http://openjdk.java.net/jeps/313">JEP 313</a>: <code>javah</code> was removed. <code>javac</code> can do the same job now:</p>

</blockquote>
<h1 id="terminology">Terminology<a aria-hidden="true" tabindex="-1" href="#terminology"><span class="anchor-link"> #</span></a></h1>
<p>You can look up <strong>thread safety</strong> anywhere, and you may already know it, but here is a quick restatement:</p>
<p>A function is thread-safe if, when called concurrently from multiple threads, every caller still gets a correct result.</p>
<h1 id="main-factors">Main factors<a aria-hidden="true" tabindex="-1" href="#main-factors"><span class="anchor-link"> #</span></a></h1>
<p>Thread-safety problems appear when <strong>a call must mutate shared state</strong>.</p>
<p>That covers four cases:</p>
<ul>
<li>Static Java native call mutating shared C++ data</li>
<li>Static Java native call mutating shared Java data</li>
<li>Instance Java native call mutating shared C++ data</li>
<li>Instance Java native call mutating shared Java data</li>
</ul>
<p>Any shared data can create thread-safety issues.</p>
<blockquote>
<p>Static vs instance native calls: if the native method is <code>static</code>, it is a class-level call; otherwise it is an instance call.</p>
<p>Shared C++ data means globals (or other globally reachable state). Shared Java data here means fields on a Java class or object that C++ reads or writes through JNI.</p>
</blockquote>

<p><code>threadSafe()</code> remains correct under any number of concurrent calls. <code>threadUnsafe()</code> and <code>threadUnsafe2()</code> are not thread-safe — under many threads you get scrambled results.</p>

<p>In the first function, marker 1 uses a C++ mutex — that works, but under heavy concurrency it serializes everything and hurts throughput. Marker 2 is usually preferable: the caller passes a custom object, C++ mutates that object, and as long as each caller’s object is unique, concurrent results stay correct.</p>
<p>Markers 3 and 4 are counterexamples. Marker 3 mutates shared C++ state without locking; marker 4 is similar but the shared state lives in a Java field.</p>

<h1 id="summary">Summary<a aria-hidden="true" tabindex="-1" href="#summary"><span class="anchor-link"> #</span></a></h1>
<p>Thread safety means using <strong>shared resources</strong> carefully. Prefer not sharing at all — let callers pass the values to mutate. That usually works best.</p>
