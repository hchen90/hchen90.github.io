16:T3c0d,<h1 id="introduction">Introduction<a aria-hidden="true" tabindex="-1" href="#introduction"><span class="anchor-link"> #</span></a></h1>
<p>Today let's discuss packers for PE files. A packer is mainly used for commercially protecting a PE file so that the software is less likely to be cracked. As cracking knowledge becomes widespread, packers have grown increasingly complex just to barely hold out against being broken.</p>
<p>The loading process of a packer is covered in many books; let's review it here with a diagram:</p>
<p><img src="/post/mspeshell/5053c5d77cf8.png" alt="pic1"></p>
<p>This diagram actually shows one case: the original program has been run through a compression engine. Alternatively, you can pack an EXE directly without compression, which saves the overhead of the packer's size but leaves the original EXE code uncompressed—so the file grows slightly. A third option is to insert into the gaps between the sections of the EXE: the resulting file is the same size as the original, but there are requirements on section sizes. These are the three conventional packing approaches.</p>
<p>If you just add a simple packer, the <code>AddCode</code> example in Luo Yunbin's <em>Assembly Language Programming in the Windows 32-bit Environment</em> is a typical representative. The main steps are:</p>
<p>First, add a section header entry to the section table and write the code at the end of the file (now matching the new section header). Pay attention to the section's <code>SectionAlignment</code> and <code>FileAlignment</code>; write the section header according to these two parameters, jump to the file offset corresponding to the section, and write the code. Where the code doesn't fill the section, pad with <code>0</code> to maintain file alignment (typically <code>200</code>). Finally, wrap up: increment the PE file's <code>NumberOfSections</code> by <code>1</code>; add to <code>SizeOfImage</code> the size of the new section aligned to <code>SectionAlignment</code>; align <code>SizeOfHeaders</code> to <code>FileAlignment</code>—if adding one <code>IMAGE_SECTION_HEADER</code> doesn't exceed <code>FileAlignment</code>, you may not need to change it; and <code>SizeOfCode</code> is the size of the added code, i.e. the sum of the sizes of the sections that contain code (this value is already aligned to <code>FileAlignment</code> in the section table).</p>
<p>What I just described is the second approach above. For the other two, the attachment below includes one that is similar to this approach, plus one using the third approach.</p>
<p>The method above is relatively simple to implement, but it provides no program-protection features. Next let's discuss a method with protection.</p>
<p>To implement protection, the things you can commonly protect are the import functions, export functions, code section, data section, and so on.</p>
<h1 id="how-to-protect-import-functions">How to protect import functions?<a aria-hidden="true" tabindex="-1" href="#how-to-protect-import-functions"><span class="anchor-link"> #</span></a></h1>
<p>In the <code>DataDirectory</code> of the PE header there is an import table that specifies an <code>RVA</code> and a size. Many PE analyzers—PEiD, LoadPE, and my own PE Scanner—find function information based on it.</p>
<p>After the PE file is loaded, this RVA points to an <code>IMAGE_IMPORT_DESCRIPTOR</code>, which is structured as follows:</p>

When the Windows loader loads the file, it replaces all the <code>ThunkData</code> pointed to by <code>FirstThunk</code> with the real addresses of the functions that the <code>ThunkData</code> refers to, as shown below:</p>
<p><img src="/post/mspeshell/4bf2684e3b58.png" alt="pic2"></p>
<p>Before the program is loaded, the disk file looks like this:</p>
<p><img src="/post/mspeshell/948f3eb1dd9b.png" alt="pic3"></p>
<p>At location <code>402014</code> is <code>000020F4</code>, which is an <code>RVA</code>; let's see where this <code>ThunkData</code> points, as follows:</p>
<p><img src="/post/mspeshell/00e48c9cd0f6.png" alt="pic4"></p>
<p>You can see that two bytes further on is the function name <code>ExitProcess</code>. This is an <code>IMAGE_IMPORT_BY_NAME</code> structure; the first two bytes are the <code>HINT</code>, an inconsequential <code>WORD</code> field. Now that we're roughly familiar with PE loading, note that if you write your own import-table protection, you'll have to perform these steps "by hand" in your own code.</p>

<p><img src="/post/mspeshell/5bba3bb8e98c.png" alt="pic6"></p>
<p>You can see it reaches <code>ExitProcessStub</code> in <code>Kernel32</code>, and the whole loading process is now clear.</p>
<h2 id="how-to-load-a-hidden-import-table">How to load a "hidden" import table<a aria-hidden="true" tabindex="-1" href="#how-to-load-a-hidden-import-table"><span class="anchor-link"> #</span></a></h2>
<p>So to protect the functions in the import table, you must "hide" the original import-table information (including the <code>IMAGE_IMPORT_DESCRIPTOR</code> and the series of <code>ThunkData</code>) and define your own <code>IMAGE_IMPORT_DESCRIPTOR</code> and <code>ThunkData</code> for the API functions you need. That way you don't have to do the complex work of finding Kernel32's base address in the heap, looking up export functions, and so on. For example, define your own two functions in Kernel32.dll—<code>LoadLibraryA</code> and <code>GetProcAddressA</code>—and hide the original import function information. When the program loads, you find these yourself and locate the functions in <code>FirstThunk</code>. Because the import table is "hidden," the PE loader hasn't replaced the <code>ThunkData</code> values with real function addresses like <code>754879f8</code>, so you must find the functions yourself (there are two kinds: imported by ordinal and imported by name). Note that if the function you find is imported by ordinal, you must strip the high detection bit <code>1</code> (i.e. test against <code>80000000H</code>) and then use it directly as the function name, calling <code>GetProcAddressA</code> to get the address. Getting the DLL name is even simpler and more direct: add Name's <code>RVA</code> to the base to obtain the DLL name string, which you can load with <code>LoadLibraryA</code>.</p>
<p>Through the steps above—for example, fixing up those locations like <code>402014</code>—you load <code>Kernel32.dll</code> yourself with <code>LoadLibrary</code>, get the address of <code>ExitProcess</code>, and write the obtained address into location <code>402014</code>, so that <code>ExitProcess</code> can execute properly. The same applies to the other functions; you must iterate over all the <code>IMAGE_IMPORT_DESCRIPTOR</code>s to ensure every function address is filled into the right place.</p>
<h2 id="encrypting-data-and-code">Encrypting data and code<a aria-hidden="true" tabindex="-1" href="#encrypting-data-and-code"><span class="anchor-link"> #</span></a></h2>
<p>The methods above actually only protect the import table, but anyone with a bit of disassembly skill can read the earlier code: although the program's entry point has changed, the code is still there and can be seen by changing the offset. Compare the two images below:</p>
<p>Without the code section encrypted (start is my code):</p>
<p><img src="/post/mspeshell/7ca09d572900.png" alt="pic7"></p>
<p>With the code section encrypted (start is my code):</p>
<p><img src="/post/mspeshell/999711ac8a3b.png" alt="pic8"></p>
<p>When the code section is encrypted, your own code must contain the decryption logic so the code can execute. My example here uses only simple bit rotation—<code>rol</code>, <code>ror</code>—so decryption is quite simple. To make it more complex, you could compress the code with a compression engine (<code>lz77</code>, <code>lzss</code>, or something more complex like Huffman coding), which also saves more space, or use other cryptographic principles to encrypt it; the details are up to you.</p>
<p>But this approach basically can't withstand scrutiny. ASPack, UPX, PECompact, and the one I wrote myself in the attachment all use this method.</p>
<p>This type of packer is very easy to unpack. Here's an example:</p>
<p><img src="/post/mspeshell/6076c2fd91ef.png" alt="pic9"></p>
<p>This is an ASPack-packed file. At the start, the value after the breakpoint's <code>push</code> is still <code>0</code>; by this point it has become <code>004013da</code>, which is exactly the original program's <code>ep</code>. In fact, ASPack's earlier work is much like my packer—nothing more than filling in <code>ThunkData</code> and decrypting data.</p>
<p><img src="/post/mspeshell/e475c283bee9.png" alt="pic10"></p>
<p>By this point you can see ASPack has filled in all the <code>ThunkData</code>. Dump it with OllyDump, then look at the import table information; use LoadPE to change <code>NtDllDefWindowProc_A</code> to <code>DefWindowProcA</code>, and unpacking is complete.</p>
<p>The reason this kind of packer is easy to unpack is that the shell code writes the code back to its original location after decrypting the program—like hiding something in a reliable container to protect it, but to use it you must take it out (the shell's self-decryption), and the moment it's taken out we can restore it to its original form!</p>
<p>If you designed a mechanism where, each time code needs to execute, it first reads the encrypted data, decrypts one instruction's worth of data, executes it, then fetches the next, decrypts, and executes—looping this way to the end, using only one instruction's worth of address space, with later code overwriting earlier code and short instructions padded with <code>90H</code> (<code>nop</code>)—then the decrypted data isn't recorded, improving security. But this method has to deal with the length of the next instruction, which requires a small disassembly engine embedded in the packer, plus issues like where <code>eip</code> jumps—so it gets complex.</p>
<h2 id="the-idea-of-a-virtual-machine">The idea of a virtual machine<a aria-hidden="true" tabindex="-1" href="#the-idea-of-a-virtual-machine"><span class="anchor-link"> #</span></a></h2>
<p>The problem above leads to this one. A virtual machine is a mechanism that emulates CPU instruction execution, the I/O environment, and so on—common in VM software such as VMware and VirtualBox. A packer can also use this VM mechanism, except it mainly emulates CPU instructions (and can also emulate the I/O environment). You could make the mechanism above more complex: <code>pop eax</code> goes to the VM for execution and becomes <code>dec eax</code>; <code>inc eax</code> goes to the VM and becomes <code>push eax</code>; and it can be more elaborate—emulate your own I/O environment where each <code>IN 45H</code> means <code>eax</code> plus <code>1</code>, each <code>IN 46H</code> means <code>eax</code> minus <code>1</code>, <code>IN 50H</code> means <code>ebx</code> plus <code>1</code>, and so on. (In short, emulate a brand-new instruction set. The first few ideas are just me letting my imagination run wild—don't take them too seriously. :)</p>
<p>The VM can also incorporate cryptographic encryption mechanisms, and more.</p>
<p>All in all, there's a lot to it, covering a wide range, and actually designing it would be a large undertaking—the packer's added code would probably be substantial too.</p>
<h2 id="one-final-note">One final note<a aria-hidden="true" tabindex="-1" href="#one-final-note"><span class="anchor-link"> #</span></a></h2>
<p>If the packed program is one with a randomized load base address, it may affect the proper execution of your decrypted code. In that case you need to fix the PE by removing the <code>.reloc</code> section—mainly zeroing out the random-relocation data entry in the <code>DataDirectory</code>, decrementing <code>NumberOfSections</code> by <code>1</code>, and fixing <code>SizeOfHeaders</code>. You may not need to fix it, but most importantly you must zero out the <code>DllCharacteristics</code> value in the <code>OptionalHeader</code>.</p>
<p>Two of the items in the attachment add code into the free gaps of the program, so the program's free gaps must be fairly large or it will fail.</p>
