16:T1d40,<h1 id="what-is-a-core-dump">What Is a Core Dump?<a aria-hidden="true" tabindex="-1" href="#what-is-a-core-dump"><span class="anchor-link"> #</span></a></h1>
<p>A <strong>core dump</strong> is a mechanism inherited from UNIX. When a program crashes due to an error, it saves a snapshot of the stack, memory, PID, UID, GID, timestamp, and other information, typically used for diagnosis and debugging. <strong>Core dump</strong> data is usually kept on the machine for about three days (depending on system settings); if you don't track down the bug in time, the system deletes these <strong>core dumps</strong> after that.</p>
<h1 id="what-tools-do-you-need">What Tools Do You Need?<a aria-hidden="true" tabindex="-1" href="#what-tools-do-you-need"><span class="anchor-link"> #</span></a></h1>
<p>Generally, objdump and gdb are all you need. For diagnosis, the original source code is best (the unmodified code from when the core was dumped).</p>
<h1 id="case-study">Case Study<a aria-hidden="true" tabindex="-1" href="#case-study"><span class="anchor-link"> #</span></a></h1>
<p>Below is a failure case I'm sharing for reference.</p>
<h2 id="the-program-crashed">The Program Crashed<a aria-hidden="true" tabindex="-1" href="#the-program-crashed"><span class="anchor-link"> #</span></a></h2>
<p>This program runs without any problems; it just occasionally crashes on exit. That's the most frustrating kind. Hidden bugs like this don't trigger in most situations, then suddenly happen under some special condition. The dilemma comes down to two things:</p>
<ul>
<li>Hard to confirm (whether it happens)</li>
<li>Hard to locate</li>
</ul>

<h2 id="trying-to-debug-directly-with-coredumpctl">Trying to Debug Directly with coredumpctl<a aria-hidden="true" tabindex="-1" href="#trying-to-debug-directly-with-coredumpctl"><span class="anchor-link"> #</span></a></h2>
<p><em>coredumpctl</em> is one of the systemd tools; any system using systemd should have it. It is very easy to use. For help, run:</p>

<h2 id="disassembling-the-program">Disassembling the Program<a aria-hidden="true" tabindex="-1" href="#disassembling-the-program"><span class="anchor-link"> #</span></a></h2>
<p>When disassembling the original crashed binary, don't forget the <code>--source</code> flag; otherwise you get pure assembly and searching is much less efficient. Run:</p>
<div class="code-block-wrapper"><div class="code-block-header"><span class="code-block-lang">bash</span><button class="copy-button" data-copy-state="copy" aria-label="Copy code to clipboard" type="button" onclick="copyCode(this)"><span class="copy-button-text">Copy</span></button></div><pre><code class="hljs language-bash">objdump --<span class="hljs-built_in">source</span> -d xxxx | less

<p>Again, xxxx is the program file name.</p>
</blockquote>
<p>Now, in <code>less</code>, search for each stack address in turn (see Figure 2) and go to the first faulting location in the program right after returning from <code>libc</code>, i.e. file offset <code>0x42ce8</code>. The error is immediately pinned down (following the addresses up the stack, you can tell it's a <code>clear</code> on a <code>list</code>). It turned out to be a C++ class destructor failing while destroying a <code>list</code>. This in turn showed the bug was actually caused by multithreading: a worker thread in the program was also freeing resources, and the main thread and worker thread freed them at the same time without synchronization, so it sometimes worked and sometimes crashed.
