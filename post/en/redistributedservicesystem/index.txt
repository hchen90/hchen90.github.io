16:T4737,<h1 id="overview-and-definition">Overview and definition<a aria-hidden="true" tabindex="-1" href="#overview-and-definition"><span class="anchor-link"> #</span></a></h1>
<p>A distributed system is a system made up of a group of independent computers (nodes) working together over a network. Together they accomplish a business goal and present themselves to users as a "single system". From the user's point of view, a distributed system should be as transparent as possible: users shouldn't need to know which machine handled a request or where the data lives, and they shouldn't notice nodes being added, removed, or migrated.</p>
<p>In one sentence:</p>
<blockquote>
<p><strong>Distributed system = multiple independent computers, cooperating over a network, that look like one system from the outside</strong></p>
</blockquote>
<p>Two points to remember:</p>
<ul>
<li>Multiple nodes cooperate to achieve the same business goal.</li>
<li>From the outside, it behaves as much like a single whole as possible (transparency).</li>
</ul>
<blockquote>
<p>Note: distributed system design often requires trade-offs among consistency, availability, and partition tolerance (CAP). In practice, "eventual consistency" is widely adopted in exchange for high availability and scalability.</p>
</blockquote>
<h2 id="compared-with-a-centralized-cs-architecture">Compared with a centralized C/S architecture<a aria-hidden="true" tabindex="-1" href="#compared-with-a-centralized-cs-architecture"><span class="anchor-link"> #</span></a></h2>
<p>A centralized (monolithic) C/S architecture:</p>
<p><img src="/post/redistributedservicesystem/a98ad925f117.png" alt="Traditional C/S system"></p>
<p>A typical distributed system:</p>
<p><img src="/post/redistributedservicesystem/29d8d45dfd6d.png" alt="Distributed system"></p>
<h2 id="why-distributed-systems-are-hard">Why distributed systems are "hard"<a aria-hidden="true" tabindex="-1" href="#why-distributed-systems-are-hard"><span class="anchor-link"> #</span></a></h2>
<p>Every assumption from single-machine systems breaks down in a distributed setting 👇</p>
<h3 id="on-a-single-machine-you-assume">On a single machine you assume:<a aria-hidden="true" tabindex="-1" href="#on-a-single-machine-you-assume"><span class="anchor-link"> #</span></a></h3>
<ul>
<li>Memory is reliable</li>
<li>Clocks are consistent</li>
<li>Calls always succeed</li>
</ul>
<h3 id="in-a-distributed-system-reality-is">In a distributed system, reality is:<a aria-hidden="true" tabindex="-1" href="#in-a-distributed-system-reality-is"><span class="anchor-link"> #</span></a></h3>
<ul>
<li>The network can fail</li>
<li>Nodes can crash</li>
<li>Clocks are out of sync</li>
<li>Messages can be lost / duplicated / delayed</li>
</ul>
<p>👉 <strong>Distributed system = building a reliable system in an "untrustworthy environment"</strong></p>
<h2 id="the-core-problems-a-distributed-system-must-solve">The core problems a distributed system must solve<a aria-hidden="true" tabindex="-1" href="#the-core-problems-a-distributed-system-must-solve"><span class="anchor-link"> #</span></a></h2>
<h3 id="1️⃣-communication">1️⃣ Communication<a aria-hidden="true" tabindex="-1" href="#1️⃣-communication"><span class="anchor-link"> #</span></a></h3>
<p>How do nodes talk to each other?</p>
<ul>
<li>HTTP / RPC / gRPC</li>
<li>Message queues (Kafka / RocketMQ / RabbitMQ)</li>
</ul>
<hr>
<h3 id="2️⃣-state-consistency-the-most-central">2️⃣ State consistency (the most central)<a aria-hidden="true" tabindex="-1" href="#2️⃣-state-consistency-the-most-central"><span class="anchor-link"> #</span></a></h3>
<p>How do you keep data consistent across multiple machines?</p>
<ul>
<li>Strong consistency (bank transfers)</li>
<li>Eventual consistency (likes, recommendations)</li>
</ul>
<p>👉 This leads directly to the <strong>CAP theorem</strong></p>
<hr>
<h3 id="3️⃣-fault-tolerance">3️⃣ Fault tolerance<a aria-hidden="true" tabindex="-1" href="#3️⃣-fault-tolerance"><span class="anchor-link"> #</span></a></h3>
<p>What happens when a machine goes down?</p>
<ul>
<li>Replicas</li>
<li>Automatic failover</li>
<li>Retries / timeouts</li>
</ul>
<hr>
<h3 id="4️⃣-scalability">4️⃣ Scalability<a aria-hidden="true" tabindex="-1" href="#4️⃣-scalability"><span class="anchor-link"> #</span></a></h3>
<p>What if traffic grows 10×?</p>
<ul>
<li>Add machines (horizontal scaling)</li>
<li>Load balancing (load balancer)</li>
</ul>
<blockquote>
<h2 id="the-cap-theorem-the-law-of-physics-of-distributed-systems">The CAP theorem (the "law of physics" of distributed systems)<a aria-hidden="true" tabindex="-1" href="#the-cap-theorem-the-law-of-physics-of-distributed-systems"><span class="anchor-link"> #</span></a></h2>
<p>When a network partition (P) occurs, <strong>you can only choose one of C and A</strong></p>
<ul>
<li><strong>C (Consistency)</strong></li>
<li><strong>A (Availability)</strong></li>
<li><strong>P (Partition tolerance)</strong>: mandatory</li>
</ul>
<p>Real-world systems:</p>
<ul>
<li><strong>Financial systems</strong> → CP</li>
<li><strong>Social / recommendation</strong> → AP</li>
</ul>
</blockquote>
<h1 id="design-overview">Design overview<a aria-hidden="true" tabindex="-1" href="#design-overview"><span class="anchor-link"> #</span></a></h1>
<ul>
<li>Message-driven: treat messages as the "first-class citizen" of inter-service collaboration; naturally decoupled and easy to scale.</li>
<li>Actor model: model service instances as Actors that process messages and maintain their own state, isolating concurrency.</li>
<li>MongoDB/Postgres: models that fit business objects, with support for sharding and partitioning, which helps scalability and high availability.</li>
<li>Redis: a high-speed cache for read/write hotspots; can also handle rate limiting, short-lived queues, and similar roles.</li>
<li>Kafka/RocketMQ: message channels between producers and consumers.</li>
<li>Engineering principles: clear boundaries, single responsibility, idempotency and retries, and statelessness wherever possible (especially at the gateway layer).</li>
</ul>
<hr>
<h2 id="the-actor-model">The Actor model<a aria-hidden="true" tabindex="-1" href="#the-actor-model"><span class="anchor-link"> #</span></a></h2>
<p>In practical engineering terms, the theoretical Actor corresponds to a microservice submodule with its own state.</p>
<blockquote>
<p>See Wikipedia: <a href="https://en.wikipedia.org/wiki/Actor_model">Actor Model</a></p>
</blockquote>
<p>An Actor is a basic unit of computation:</p>
<ul>
<li>It receives messages (Mailbox).</li>
<li>It processes messages based on its current state and behavior (Behavior + State).</li>
<li>It produces a new state and, optionally, response messages.</li>
</ul>
<p>Actors are isolated from each other, share no memory, and cooperate purely through messages. This model is especially well suited to highly concurrent, strongly isolated distributed scenarios.</p>
<p><img src="/post/redistributedservicesystem/1104498e5f0a.png" alt="Actor Model"></p>
<p>In the system's layering, "Service N" can be modeled as a group of Actors: each service is split into several single-responsibility Actors handling sub-domain logic such as sessions, orders, inventory, and settlement. This reduces coupling and makes scaling easier.</p>
<h3 id="state-machines-fsm-and-actors">State machines (FSM) and Actors<a aria-hidden="true" tabindex="-1" href="#state-machines-fsm-and-actors"><span class="anchor-link"> #</span></a></h3>
<p>Logic inside many Actors can be organized as a finite state machine (FSM). The four elements of an FSM:</p>
<ul>
<li>State</li>
<li>Event</li>
<li>Action</li>
<li>Transition</li>
</ul>
<p>A state machine starts from the "initial state", moves to the next state when an event fires and performs the corresponding action, and eventually reaches the "final state". Treating the state machine as a "black box" that exposes only events and results achieves good isolation of internal information and state safety.</p>
<hr>
<h2 id="data-layer-mongodbpostgres">Data layer: MongoDB/Postgres<a aria-hidden="true" tabindex="-1" href="#data-layer-mongodbpostgres"><span class="anchor-link"> #</span></a></h2>
<p>MongoDB is a very good fit for distributed systems:</p>
<ul>
<li>Its data model (Document/Collection/Table) is close to the <strong>object structure</strong> of the business, making reads and writes natural.</li>
<li>Sharding is built for horizontal scaling, distributing data evenly across nodes by key.</li>
<li>Replica sets provide high availability and read/write splitting strategies.</li>
<li>Consistency and transactions: multi-document transactions are supported, but in practice "eventual consistency + idempotent compensation" is often used to reduce coupling and overhead.</li>
</ul>
<p><img src="/post/redistributedservicesystem/7ea8177a86d6.png" alt="MongoDB CLI"></p>
<p>Practical recommendations:</p>
<ul>
<li>Design the shard key carefully (high cardinality, even writes, high query hit rate).</li>
<li>Base read/write strategy on replica set roles (write to primary, read from secondaries).</li>
<li>Use sensible indexes and TTL indexes to manage hot and historical data.</li>
</ul>
<blockquote>
<p>Use an ORM well; in Go, gorm is very popular.</p>
</blockquote>
<h2 id="cache-layer-redis">Cache layer: Redis<a aria-hidden="true" tabindex="-1" href="#cache-layer-redis"><span class="anchor-link"> #</span></a></h2>
<p>Redis's role in this architecture:</p>
<ul>
<li>Hot data cache: reduces database load and improves read performance (using strategies such as Cache-Aside / Read-Through / Write-Through).</li>
<li>Short-lived queues and rate limiting: simple queues and rate limiting based on List / Stream / token bucket.</li>
<li>Sessions and transient state: store short-lived sessions, idempotency tokens, distributed locks, etc.</li>
</ul>
<p><img src="/post/redistributedservicesystem/b23b8e305828.png" alt="Redis CLI"></p>
<p>Typical risks and countermeasures:</p>
<ul>
<li>Cache penetration: cache null values for non-existent keys + a Bloom filter.</li>
<li>Cache breakdown (hot-key expiry): use mutex-guarded refresh for hot keys, or logical expiry + background refresh.</li>
<li>Cache avalanche: randomize expiration times, and set up multi-level rate limiting and degradation strategies.</li>
</ul>
<hr>
<h2 id="service-discovery-and-configuration-etcd">Service discovery and configuration: etcd<a aria-hidden="true" tabindex="-1" href="#service-discovery-and-configuration-etcd"><span class="anchor-link"> #</span></a></h2>
<p>etcd is a distributed key-value store based on the Raft consensus algorithm, commonly used for service registration and discovery, dynamic configuration, and distributed coordination:</p>
<ul>
<li>Service registration and discovery:
<ul>
<li>Registration: instances write their address and metadata under <code>/services/{name}/{instanceId}</code> with a lease (Lease + TTL) and send periodic KeepAlives.</li>
<li>Discovery: the gateway or callers Watch the corresponding prefix to detect instances coming online or going offline, and update local routing.</li>
<li>Robustness: keys are deleted automatically when the lease expires, avoiding "zombie instances"; clients should reconnect with exponential backoff and jitter.</li>
</ul>
</li>
<li>Dynamic configuration:
<ul>
<li>Organize configuration under the <code>/config/{app}/{env}/</code> prefix; publishers write, clients Watch and hot-reload.</li>
<li>Split large configurations into modules / load them in segments; sensitive configuration needs encryption or a dedicated configuration center.</li>
</ul>
</li>
<li>Coordination:
<ul>
<li>Distributed locks / leader election: use the etcd concurrency API (session-based Mutex/Campaign).</li>
<li>Typical uses: sharded task scheduling, single-leader writes, centralized arbitration of rate-limit quotas.</li>
</ul>
</li>
<li>Operations:
<ul>
<li>A cluster of 3 or 5 nodes is ideal (odd numbers for voting; too many nodes actually reduces write performance).</li>
<li>Configure snapshots and compaction properly to avoid an oversized Watch backlog; set timeouts and heartbeat thresholds for high-latency links.</li>
</ul>
</li>
</ul>
<p>In this architecture, etcd plays the infrastructure role of "service registration and discovery + dynamic configuration + coordination primitives", supporting gateway routing and internal service addressing.</p>
<hr>
<h2 id="communication-and-consistency-strategy">Communication and consistency strategy<a aria-hidden="true" tabindex="-1" href="#communication-and-consistency-strategy"><span class="anchor-link"> #</span></a></h2>
<ul>
<li>Communication:
- Synchronous RPC (HTTP/gRPC) for small closed loops that need strong real-time behavior and strong consistency.
- An asynchronous message bus for decoupling and smoothing traffic peaks (RocketMQ/Kafka/RabbitMQ/Redis Stream, etc.).</li>
<li>Retries and idempotency:
<ul>
<li>Retry when a downstream is briefly unavailable; every retryable write must be idempotent (dedup keys, idempotency tokens).</li>
</ul>
</li>
<li>Eventual consistency:
<ul>
<li>Saga / Outbox pattern: use a local transaction + outbound events to guarantee changes are delivered, and orchestrate compensation on failure.</li>
</ul>
</li>
<li>Global identifiers:
<ul>
<li>Snowflake / segment-cached ID generation produces sortable distributed IDs, useful for routing and auditing.</li>
</ul>
</li>
</ul>
<hr>
<h2 id="message-middleware-rocketmqkafka">Message middleware: RocketMQ/Kafka<a aria-hidden="true" tabindex="-1" href="#message-middleware-rocketmqkafka"><span class="anchor-link"> #</span></a></h2>
<p>RocketMQ/Kafka are high-performance, low-latency distributed message middleware with complete messaging semantics and enterprise features:</p>
<ul>
<li>Core concepts: Topic, Tag, Message Key, Producer Group, Consumer Group.</li>
<li>Delivery semantics: at-least-once by default; exactly-once has to be implemented at the business layer with idempotency keys / dedup tables.</li>
<li>Ordered messages: local ordering within a queue based on a sharding key, suitable for order state flows, fund ledgers, etc.</li>
<li>Transactional messages:
<ul>
<li>Flow: send a half message (Prepare) → execute the local transaction → Commit/Rollback;</li>
<li>The broker can check back on the transaction status (Transaction Check) to avoid dangling transactions; the producer must implement the check-back interface;</li>
<li>Commonly used for reliable event publishing in Saga/Outbox.</li>
</ul>
</li>
<li>Delayed / scheduled messages: built-in multi-level delays; combined with retry policies to implement flexible transactions and peak shaving.</li>
<li>Retries and dead letters:
<ul>
<li>Failed consumption is redelivered per the retry policy; beyond the threshold, messages go to the DLQ (dead-letter queue) for troubleshooting and manual compensation.</li>
</ul>
</li>
<li>Consumption modes: clustering (load-balanced) and broadcasting (every consumer receives all); business consumers usually use clustering mode.</li>
<li>Design recommendations:
<ul>
<li>Idempotent messages: deduplicate with a business-unique key (such as an order number); consumers "check for duplicates first, then execute".</li>
<li>Load and scaling: plan the number of queues based on throughput and ordering needs; avoid overly large messages (&#x3C; 1MB recommended); put large objects in storage and only references in messages.</li>
<li>Observability: enable message tracing and metrics reporting; watch backlog, latency, and check-back ratio.</li>
</ul>
</li>
</ul>
<p>In this architecture, RocketMQ/Kafka serves as the "event bus", supporting cross-service decoupling, peak shaving, and eventual consistency:</p>
<ul>
<li>Outbox: business table + outbox table committed in one local transaction, published to RocketMQ in the background, and stored idempotently on the consumer side.</li>
<li>Saga: an orchestrator advances/rolls back steps based on events, with compensation messages on failure.</li>
</ul>
<hr>
<h2 id="topology-and-deployment">Topology and deployment<a aria-hidden="true" tabindex="-1" href="#topology-and-deployment"><span class="anchor-link"> #</span></a></h2>
<p>Typical topology:</p>
<ul>
<li>Gateway: the single external entry point, handling authentication, routing, rate limiting, and aggregation.</li>
<li>Service registration and discovery: an etcd-based registry with Watch, providing dynamic addressing and health checks (optionally with sidecars).</li>
<li>Internal services: domain-partitioned microservices / Actor groups that interact via RPC/messages.</li>
<li>Data and cache layer: a MongoDB cluster + Redis cluster, designed with replica sets, Sentinel, and sharding.</li>
<li>Messaging layer: a RocketMQ broker cluster + NameServer, scaling throughput by Topic/queue.</li>
</ul>
<p><img src="/post/redistributedservicesystem/a5b1f3959027.png" alt="Architecture diagram"></p>
<hr>
<h2 id="when-it-fits">When it fits<a aria-hidden="true" tabindex="-1" href="#when-it-fits"><span class="anchor-link"> #</span></a></h2>
<ul>
<li>Large numbers of concurrent connections (massive user bases, IoT devices, game gateways, etc.).</li>
<li>Large data volumes requiring horizontal scaling and elasticity (logging / order / content platforms, etc.).</li>
<li>Hard high-availability requirements (parts of financial payments, read paths of core transactions, etc.).</li>
</ul>
<hr>
<h2 id="summary">Summary<a aria-hidden="true" tabindex="-1" href="#summary"><span class="anchor-link"> #</span></a></h2>
<p>This "message-driven + Actor + MongoDB/Redis" combination has a clear engineering path and a mature ecosystem: when performance falls short, scale out by adding nodes; when data grows, scale with MongoDB sharding; when read/write load is uneven, use Redis caching and rate limiting to shave peaks. The real difficulty is not "whether it works", but "whether it can be scaled and operated gracefully".</p>
