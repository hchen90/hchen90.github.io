16:T30f1,<p>In systems programming, the I/O (input/output) model determines how you interact with data, and it has a critical impact on overall system performance. The I/O model directly affects several major areas:</p>
<ul>
<li>Throughput</li>
<li>Machine resource utilization, e.g. CPU usage</li>
<li>System scalability</li>
<li>Programming complexity</li>
</ul>
<p>In network programming, the I/O model is the foundation of a high-performance server. If it's poorly designed, no matter how elegant the upper layers are, everything stalls at the I/O layer and becomes the performance bottleneck.</p>
<p>This post focuses on two core I/O models on Linux—synchronous and asynchronous I/O—and explains them alongside the relevant socket functions.</p>
<h2 id="part-1-synchronous-iothe-familiar-blocking-and-non-blocking">Part 1: Synchronous I/O—the familiar "blocking" and "non-blocking"<a aria-hidden="true" tabindex="-1" href="#part-1-synchronous-iothe-familiar-blocking-and-non-blocking"><span class="anchor-link"> #</span></a></h2>
<p>In plain terms, synchronous I/O means: after the caller initiates an I/O operation, it must wait for the data to be ready before it can continue.</p>
<h3 id="core-sub-model-1-blocking-io">Core sub-model 1: Blocking I/O<a aria-hidden="true" tabindex="-1" href="#core-sub-model-1-blocking-io"><span class="anchor-link"> #</span></a></h3>
<p>In Linux, a socket created with <code>socket()</code> is in blocking mode by default. In this mode, when you call <code>recv()</code>, <code>read()</code>, or <code>accept()</code> and the data isn't ready, the process is suspended into a blocked state until the data becomes ready, at which point the process resumes.</p>
<blockquote>
<p>"Process suspension" here means thread suspension in a multithreaded scenario.</p>
</blockquote>
<p>This approach has pros and cons. The upside is that it's simple to program—the logic is intuitive and easy to understand. The downside is low efficiency: especially under high concurrency, a single thread can handle only one connection, which fails to make full use of the CPU.</p>
<h3 id="core-sub-model-2-non-blocking-io">Core sub-model 2: Non-blocking I/O<a aria-hidden="true" tabindex="-1" href="#core-sub-model-2-non-blocking-io"><span class="anchor-link"> #</span></a></h3>
<p>On Linux, non-blocking I/O is enabled by using <code>fcntl()</code> to put the socket into non-blocking mode. Once that takes effect, if the data isn't ready the caller immediately gets an error return (usually <code>EAGAIN</code> or <code>EWOULDBLOCK</code>); the calling thread isn't suspended and can go do other work.</p>
<p>The advantage here is obvious: the thread doesn't block, so it can handle many more tasks and make much better use of the CPU. But the downside is equally clear: it needs some kind of continuous polling to check whether the I/O data is ready, which also burns CPU.</p>
<h3 id="a-summary-of-the-two-modes">A summary of the two modes<a aria-hidden="true" tabindex="-1" href="#a-summary-of-the-two-modes"><span class="anchor-link"> #</span></a></h3>
<p>The essence of synchronous I/O is that <strong>after issuing an I/O request, the caller must wait for the data copy to complete</strong>. Blocking and non-blocking are just different strategies for the stage of waiting for the data to become ready.</p>
<h2 id="part-2-asynchronous-iolet-the-os-handle-io-for-you">Part 2: Asynchronous I/O—let the OS handle I/O for you<a aria-hidden="true" tabindex="-1" href="#part-2-asynchronous-iolet-the-os-handle-io-for-you"><span class="anchor-link"> #</span></a></h2>
<p>In Part 1 we saw that blocking I/O has low CPU utilization, while non-blocking I/O is complex to control and its mechanism also consumes a lot of CPU. To solve these problems more effectively, OS-level asynchronous I/O was introduced.</p>
<p>The flow is as follows: after the caller initiates the I/O operation, it can return immediately and continue with other tasks. When the I/O operation <strong>completes</strong>, the OS notifies the caller through some mechanism (such as a callback). It's like ordering takeout—you can keep working, and you get a notification when it arrives.</p>
<p>This way, the OS solves the control complexity and CPU consumption of non-blocking I/O for us.</p>
<p>Here we introduce Linux's asynchronous I/O mechanisms. Note that they are meant for reading disk block devices, not for network I/O; the goal is to illustrate the idea of asynchronous I/O on Linux. Asynchronous I/O breaks down into the following steps:</p>
<h3 id="step-1-issue-the-asynchronous-io-request">Step 1: Issue the asynchronous I/O request<a aria-hidden="true" tabindex="-1" href="#step-1-issue-the-asynchronous-io-request"><span class="anchor-link"> #</span></a></h3>
<p>The flow for issuing asynchronous I/O:</p>
<ol>
<li>The application calls a special asynchronous I/O request function (e.g. <code>aio_read()</code> or <code>io_submit()</code>).</li>
<li>This call immediately submits the I/O request (including the file descriptor to read, the buffer address, the data size, and so on) to the <strong>kernel</strong>.</li>
<li>This is the key step. The submission function <strong>returns immediately</strong> rather than waiting for the data read/write to complete. This means the application can keep doing other tasks without having to stop.</li>
</ol>
<blockquote>
<p>LibAIO vs. Linux native asynchronous I/O functions</p>
<p>LibAIO is POSIX-compliant and has better cross-platform support, but it actually simulates asynchrony using a thread pool, so its performance is not ideal. Typical functions:</p>
<ul>
<li><code>aio_read()</code></li>
<li><code>aio_write()</code></li>
<li><code>aio_fsync()</code></li>
<li><code>aio_error()</code></li>
<li><code>aio_return()</code></li>
<li><code>aio_suspend()</code></li>
<li><code>aio_cancel()</code></li>
<li><code>aio_listio()</code></li>
</ul>
<p>Linux's native asynchronous I/O functions are a more direct and efficient way to interact with the kernel. They submit I/O requests directly into the kernel's event queue instead of relying on thread simulation, achieving true kernel-level asynchrony. Their main drawback is that they only run on Linux and are not portable. Typical functions:</p>
<ul>
<li><code>io_setup()</code></li>
<li><code>io_getevents()</code></li>
<li><code>io_submit()</code></li>
<li><code>io_cancel()</code></li>
<li><code>io_destroy()</code></li>
</ul>
</blockquote>
<h3 id="step-2-the-kernel-takes-over-and-processes-the-io">Step 2: The kernel takes over and processes the I/O<a aria-hidden="true" tabindex="-1" href="#step-2-the-kernel-takes-over-and-processes-the-io"><span class="anchor-link"> #</span></a></h3>
<p>Once the request is submitted, the rest of the work is done by the kernel, and the application hardly needs to worry about it.</p>
<ul>
<li><strong>Kernel scheduling</strong>: After receiving the request, the kernel puts it in a queue and schedules an appropriate time to handle it.</li>
<li><strong>Hardware interaction</strong>: The kernel interacts with the hardware (such as the disk controller) to start the data transfer. This happens entirely in the background and usually requires no CPU involvement (via <strong>DMA, Direct Memory Access</strong>).</li>
<li><strong>Data copy</strong>: Data is copied directly from the hardware device into the memory buffer specified by the application. The copy is handled entirely by the kernel, with no application involvement.</li>
</ul>
<h3 id="step-3-the-io-operation-completes-and-notifies">Step 3: The I/O operation completes and notifies<a aria-hidden="true" tabindex="-1" href="#step-3-the-io-operation-completes-and-notifies"><span class="anchor-link"> #</span></a></h3>
<p>Once the copy is done, the kernel needs to notify the application in some way to tell it "your I/O task is complete."</p>
<p><strong>Notification mechanism</strong>: This is the heart of the asynchronous I/O model. There are several ways to notify:</p>
<ul>
<li><strong>Signal</strong>: The kernel can send the application a signal (e.g. <code>SIGIO</code>) to indicate the I/O task is complete. The application must register a signal handler in advance to catch it.</li>
<li><strong>Callback function</strong>: This is the more common way. When issuing the request, the application provides the address of a callback. When the I/O completes, the kernel <strong>calls it automatically</strong>, passing the result (such as success or failure) as an argument.</li>
</ul>
<h3 id="step-4-the-application-handles-the-result">Step 4: The application handles the result<a aria-hidden="true" tabindex="-1" href="#step-4-the-application-handles-the-result"><span class="anchor-link"> #</span></a></h3>
<p>Once the application receives the completion notification, it can safely process the data.</p>
<ul>
<li><strong>Check the result</strong>: After receiving the notification, the application checks the result of the operation, such as the number of bytes read or whether an error occurred.</li>
<li><strong>Continue processing</strong>: The buffer now holds the complete data, so the application can start parsing, processing, or responding to it.</li>
</ul>
<h2 id="part-3-io-multiplexingthe-dawn-of-asynchrony-in-a-synchronous-world">Part 3: I/O multiplexing—the dawn of asynchrony in a synchronous world<a aria-hidden="true" tabindex="-1" href="#part-3-io-multiplexingthe-dawn-of-asynchrony-in-a-synchronous-world"><span class="anchor-link"> #</span></a></h2>
<p>The two parts above introduced non-blocking I/O and asynchronous I/O programming. We saw that non-blocking is inefficient while asynchronous I/O programming is fairly complex. Is there a middle ground? Yes—<strong>I/O multiplexing</strong>.</p>
<p>I/O multiplexing means a single thread can simultaneously watch multiple <code>socket</code> file descriptors; when an event (data readable or writable) occurs on one of them, the kernel notifies the application layer.</p>
<p>Here we cover just a few core APIs:</p>
<ul>
<li><strong><code>select()</code></strong>: The earliest API. Its advantage is cross-platform support; its drawbacks are that performance degrades linearly with the number of <code>socket</code>s and there is a limit on the number of file descriptors.</li>
<li><strong><code>poll()</code></strong>: An improved version of <code>select()</code> that removes the file-descriptor count limit.</li>
<li><strong><code>epoll()</code></strong>: A high-performance API unique to Linux. It has two modes—<strong>edge-triggered (ET)</strong> and <strong>level-triggered (LT)</strong>—and it excels at large-scale concurrent connections because it returns only the descriptors that are already ready, without polling all of them.</li>
</ul>
<p>I/O multiplexing <strong>is still fundamentally synchronous I/O</strong> (because after the kernel notifies it, the application layer still has to issue its own <code>read()</code> or <code>write()</code> to copy the data). But by <strong>waiting for multiple file descriptors to become ready</strong>, it solves both the efficiency problem of blocking I/O and the polling problem of non-blocking I/O, achieving the efficient "one thread handling many connections" pattern.</p>
<h2 id="part-4-summary-and-choices">Part 4: Summary and choices<a aria-hidden="true" tabindex="-1" href="#part-4-summary-and-choices"><span class="anchor-link"> #</span></a></h2>
<p>Choosing among <strong>blocking I/O</strong>, <strong>non-blocking I/O</strong>, <strong>I/O multiplexing</strong>, and <strong>asynchronous I/O</strong> requires weighing several factors—programming complexity, performance, applicable scenarios, and so on—to pick the approach that fits your business.</p>
<p>General recommendations:</p>
<ul>
<li><strong>Blocking I/O</strong>: Suitable for client applications and servers with few connections and modest performance requirements.</li>
<li><strong>I/O multiplexing (especially <code>epoll</code>)</strong>: The <strong>first choice for high-concurrency servers</strong>, such as web servers and chat rooms. It strikes the best balance between programming complexity and performance.</li>
<li><strong>Asynchronous I/O</strong>: Suitable when you need extreme I/O performance and can accept the complexity of the programming model, such as databases and high-performance storage systems.</li>
</ul>
