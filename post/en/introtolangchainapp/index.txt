16:T68b8,<p>This article starts from the LangChain basics, beginning with a simple agent and working up to the concepts you need to build a production-grade agent system.</p>
<p>A traditional chatbot can only <strong>chat</strong>: its intelligence shows up as knowledge output, but it cannot <strong>make decisions on its own</strong> or <strong>call tools</strong>. Although the big AI vendors later introduced the idea of toolsets, their tool capabilities are very limited for the specifics of many businesses. When you build an agent system, the business core is not the LLM itself but the orchestration layer. LangChain is a framework for exactly that orchestration layer, and it makes agent systems much easier to implement.</p>
<h2 id="1-what-is-a-langchain-agent">1. What Is a LangChain Agent<a aria-hidden="true" tabindex="-1" href="#1-what-is-a-langchain-agent"><span class="anchor-link"> #</span></a></h2>
<h3 id="1-core-components-of-an-agent">1. Core Components of an Agent<a aria-hidden="true" tabindex="-1" href="#1-core-components-of-an-agent"><span class="anchor-link"> #</span></a></h3>
<p>In LangChain, and in AI systems more broadly, <strong>an agent is not "a model that can chat"</strong>. It is a system that can <strong>understand a goal, make decisions, and take action</strong>. A practical agent can usually be abstracted into three core components:</p>
<blockquote>
<p><strong>Agent ≈ Brain + Hands + Memory</strong></p>
</blockquote>
<h4 id="brain-thinking-and-deciding">Brain: Thinking and Deciding<a aria-hidden="true" tabindex="-1" href="#brain-thinking-and-deciding"><span class="anchor-link"> #</span></a></h4>
<p>The brain is the large language model (LLM). It differs significantly from a chat application: its job is not to answer questions and output knowledge, but to:</p>
<ul>
<li>Understand user intent</li>
<li>Break the task into steps</li>
<li>Decide whether to call a tool</li>
<li>Decide which tool to call, and how to call it (with what arguments)</li>
</ul>
<h4 id="hands-letting-the-agent-do-things">Hands: Letting the Agent "Do Things"<a aria-hidden="true" tabindex="-1" href="#hands-letting-the-agent-do-things"><span class="anchor-link"> #</span></a></h4>
<p>The hands are Tools. A tool is essentially a capability provided outside the model, with a clear function, that the model can invoke.</p>
<p>Common tools include:</p>
<ul>
<li>Search engines (looking things up)</li>
<li>Calculation (numerical computation, statistics, and so on)</li>
<li>API calls (looking up orders, sending email, and so on)</li>
<li>Database / vector retrieval (RAG)</li>
</ul>
<p>Generally speaking, the ceiling of an agent's capability is often set not by the model but by its tools.</p>
<h4 id="memory-giving-the-agent-context-awareness">Memory: Giving the Agent "Context Awareness"<a aria-hidden="true" tabindex="-1" href="#memory-giving-the-agent-context-awareness"><span class="anchor-link"> #</span></a></h4>
<p>Once started, an agent—like a chatbot—accumulates a large amount of context as the conversation continues. If the agent cannot load previously saved context each time it starts, it begins from zero, and complex business processes cannot resume after an interruption. So it is essential for an agent to be able to save context and remember.</p>
<p>An agent's memory typically includes:</p>
<ul>
<li>Short-term memory: the current conversation context, usually kept in memory.</li>
<li>State information: intermediate results and completed steps.</li>
<li>Long-term memory: user preferences and historical behavior.</li>
</ul>
<blockquote>
<p>Memory here is not the same as stuffing the entire conversation context into the prompt. Real memory selectively remembers the important information.</p>
</blockquote>
<p>These three components cooperate through a core loop, shown below.</p>
<p><img src="/post/introtolangchainapp/cbeab51fa0fb.png" alt="Agent core loop"></p>
<h3 id="2-the-basic-execution-flow-of-an-agent-in-langchain">2. The Basic Execution Flow of an Agent in LangChain<a aria-hidden="true" tabindex="-1" href="#2-the-basic-execution-flow-of-an-agent-in-langchain"><span class="anchor-link"> #</span></a></h3>
<p>In LangChain, <strong>an agent is not an object you call directly</strong>. What actually drives the agent is the <strong>AgentExecutor</strong>.</p>
<p>Before looking at AgentExecutor, consider an example that does not use a LangChain agent but instead calls the LLM manually to perform a tool call, as shown below.</p>
<p><img src="/post/introtolangchainapp/637d648535f2.png" alt="Calling a tool manually with an LLM"></p>
<p>As you can see, interacting with the LLM to use a tool takes a lot of tedious work (appending the tool call ID and the manually obtained result to the context messages) before the model can use the tool's output. LangChain's AgentExecutor is a high-level wrapper that not only solves this, but also handles other errors and exceptions.</p>
<p><img src="/post/introtolangchainapp/36b844684450.png" alt="Invoking an agent"></p>
<p>As shown above, all the tedious work under the agent is handled automatically; we only need to care about the flow and the result.</p>
<p>First, here are the four main responsibilities of AgentExecutor:</p>
<h4 id="1-driving-the-agents-reasoning-loop">1. Driving the Agent's Reasoning Loop<a aria-hidden="true" tabindex="-1" href="#1-driving-the-agents-reasoning-loop"><span class="anchor-link"> #</span></a></h4>
<p>The core of an agent is not a single model call but a loop:</p>
<ol>
<li>Pass the current input + context to the agent (LLM)</li>
<li>Parse the model output and decide whether the next step is to:
<ul>
<li>Give the final answer directly</li>
<li>Or call a tool</li>
</ul>
</li>
<li>If a tool call is needed:
<ul>
<li>Run the tool</li>
<li>Get the result</li>
<li>Feed the result back to the agent</li>
</ul>
</li>
<li>Enter the next round of reasoning</li>
</ol>
<p>This loop is not run by the model; it is run by AgentExecutor.</p>
<h4 id="2-orchestrating-and-executing-tool-calls">2. Orchestrating and Executing Tool Calls<a aria-hidden="true" tabindex="-1" href="#2-orchestrating-and-executing-tool-calls"><span class="anchor-link"> #</span></a></h4>
<p>AgentExecutor is the heart of the agent. Its responsibilities are:</p>
<ul>
<li>Match the model output to the corresponding Tool</li>
<li>Validate the arguments</li>
<li>Run the tool function</li>
<li>Capture the tool function's result or exception</li>
<li>Wrap the result</li>
</ul>
<p>So AgentExecutor automatically performs the steps from the Jupyter demo above, and does so in a more standardized and elegant way.</p>
<h4 id="3-managing-context-and-intermediate-state">3. Managing Context and Intermediate State<a aria-hidden="true" tabindex="-1" href="#3-managing-context-and-intermediate-state"><span class="anchor-link"> #</span></a></h4>
<p>Besides wrapping the tool-calling steps, AgentExecutor also maintains, throughout the session, the current conversation history, intermediate reasoning results, Memory reads and writes, and a record of executed steps.</p>
<p>This information determines what the LLM can see and whether the agent falls into an infinite loop, and it is also useful for debugging and observability.</p>
<h4 id="4-runtime-control-and-safeguards">4. Runtime Control and Safeguards<a aria-hidden="true" tabindex="-1" href="#4-runtime-control-and-safeguards"><span class="anchor-link"> #</span></a></h4>
<p>In real systems, AgentExecutor also has some fallback responsibilities that act as controls and safeguards.</p>
<p>These include:</p>
<ul>
<li>Maximum iterations (to prevent infinite loops)</li>
<li>Timeout control</li>
<li>Error handling and retries</li>
<li>Logging</li>
</ul>
<h2 id="2-from-0-to-1-building-a-basic-agent">2. From 0 to 1: Building a Basic Agent<a aria-hidden="true" tabindex="-1" href="#2-from-0-to-1-building-a-basic-agent"><span class="anchor-link"> #</span></a></h2>
<p>The sections above explained the basic concepts of LangChain agents and the structure of their core.</p>
<p>The approach to building such an agent is then clear: follow the agent's core components so that it becomes an entity that can think and use tools, in three steps.</p>
<h3 id="1-choose-a-base-model-llm-model">1. Choose a Base Model (LLM Model)<a aria-hidden="true" tabindex="-1" href="#1-choose-a-base-model-llm-model"><span class="anchor-link"> #</span></a></h3>
<p>Model choice is crucial for an agent. There are generally two types:</p>
<ul>
<li>Chat models</li>
<li>Instruct models</li>
</ul>
<p>They differ a lot. Chat models are optimized for <strong>multi-turn conversation</strong> and are good at understanding context, roles, and conversation state. Instruct models are optimized for <strong>following instructions</strong> and are good at getting a task right, reliably, in one shot.</p>
<p>For example, deepseek-chat is a chat model, while mistral-small-24b-instruct is an instruct model.</p>
<p>The capabilities that matter most for an agent are instruction following and stable Tool Calling.</p>
<h3 id="2-give-the-agent-tools">2. Give the Agent Tools<a aria-hidden="true" tabindex="-1" href="#2-give-the-agent-tools"><span class="anchor-link"> #</span></a></h3>
<p>A Tool is essentially a function with a description. Each Tool has a corresponding Tool Schema that describes the function, and it directly affects the agent's behavior.</p>
<p>Tool design takes care. If tools are poorly designed, the agent will misuse them (the Tool Schema should describe each function clearly, and when there are several tools, their responsibilities should be clearly separated).</p>
<p>From these three steps, we can see that a working agent needs:</p>
<ul>
<li>The ability to think</li>
<li>Tools</li>
<li>The ability to understand context</li>
</ul>
<p>The figure below shows how a Tool is defined.</p>
<p><img src="/post/introtolangchainapp/783d8547cfc6.png" alt="Defining a tool"></p>
<p>Once defined, <code>tool1</code> can be referenced directly by a model or agent.</p>
<h3 id="3-short-term-memory">3. Short-Term Memory<a aria-hidden="true" tabindex="-1" href="#3-short-term-memory"><span class="anchor-link"> #</span></a></h3>
<p>Short-term memory lets an agent be interrupted and later resume without losing earlier results and information. LLMs are stateless: if you do not provide the old chat history, the model does not know it.</p>
<p>The memory here is short-term memory stored in RAM and not persisted to disk; its purpose is to feed the LLM. Persisted storage belongs to a different category: vector databases.</p>
<p>The figure below shows how to set up and use a short-term conversation store.</p>
<p><img src="/post/introtolangchainapp/11d7511a6c5f.png" alt="Short-term memory"></p>
<h2 id="3-from-a-single-agent-to-an-intelligent-system">3. From a "Single Agent" to an "Intelligent System"<a aria-hidden="true" tabindex="-1" href="#3-from-a-single-agent-to-an-intelligent-system"><span class="anchor-link"> #</span></a></h2>
<p>Now let's move from a single agent to a system-level perspective.</p>
<h3 id="1-long-running-context-and-state">1. Long-Running Context and State<a aria-hidden="true" tabindex="-1" href="#1-long-running-context-and-state"><span class="anchor-link"> #</span></a></h3>
<p>Context here involves distinguishing two concepts: Context and Prompt.</p>
<h4 id="what-is-a-prompt">What Is a Prompt<a aria-hidden="true" tabindex="-1" href="#what-is-a-prompt"><span class="anchor-link"> #</span></a></h4>
<p>A prompt is the <strong>input to a single model call; its lifetime is limited to that one call</strong>.</p>
<h4 id="what-is-context">What Is Context<a aria-hidden="true" tabindex="-1" href="#what-is-context"><span class="anchor-link"> #</span></a></h4>
<p>Context is the <strong>set of information an agent shares across multiple steps and rounds of decisions</strong>.</p>
<p>Context can include the conversation history with the model, intermediate reasoning results, results of external tool calls, actions taken, the current task state, and so on.</p>
<p>LangChain also supports defining a special kind of context data. The example below shows how to set Context on an agent.</p>
<p><img src="/post/introtolangchainapp/d06d322aad0e.png" alt="Setting context on an agent"></p>
<p>An agent's runtime state represents its current phase and is used to decide the next action. With state, you can represent a continuously running system (much like a state machine).</p>
<p>So how do you define an agent's state in LangChain?</p>
<p>LangChain supports defining a special agent state by creating an agent with a state schema (similar to Context), as shown below.</p>
<p><img src="/post/introtolangchainapp/fcbdffb4119f.png" alt="Defining agent state"></p>
<p>Both invocation styles achieve the same effect.</p>
<p><img src="/post/introtolangchainapp/b4ebcb566e18.png" alt="Two ways to invoke with state"></p>
<blockquote>
<p>Note that the LLM is a consumer of State, not its owner.</p>
</blockquote>
<h3 id="2-introducing-the-model-context-protocol-mcp">2. Introducing the Model Context Protocol (MCP)<a aria-hidden="true" tabindex="-1" href="#2-introducing-the-model-context-protocol-mcp"><span class="anchor-link"> #</span></a></h3>
<p>As agents evolve from "one model + a few tools" to "multiple models + many tools + long-running operation", one question becomes unavoidable:</p>
<blockquote>
<p><strong>How should Context be organized, passed, and understood?</strong></p>
</blockquote>
<p>That is exactly the core problem the <strong>Model Context Protocol (MCP)</strong> sets out to solve.</p>
<p>Engineering pain points of agent systems, and how MCP addresses them:</p>
<h4 id="1-data-silos-and-fragmented-context">1. Data Silos and Fragmented "Context"<a aria-hidden="true" tabindex="-1" href="#1-data-silos-and-fragmented-context"><span class="anchor-link"> #</span></a></h4>
<ul>
<li><strong>Pain point:</strong> AI often operates in an "information vacuum". To give it project background, you have to copy and paste documents by hand, or put up with the complex setup of RAG (retrieval-augmented generation).</li>
<li><strong>Solution:</strong> MCP lets AI pull the most relevant context from local files, databases, or third-party APIs in real time and on demand, without repeatedly uploading data.</li>
</ul>
<h4 id="2-very-high-integration-maintenance-costs">2. Very High Integration Maintenance Costs<a aria-hidden="true" tabindex="-1" href="#2-very-high-integration-maintenance-costs"><span class="anchor-link"> #</span></a></h4>
<ul>
<li><strong>Pain point:</strong> APIs change often. If GitHub updates its API, every AI tool you integrated with GitHub might break.</li>
<li><strong>Solution:</strong> Developers only need to maintain one <strong>MCP Server</strong>. Once that server is updated, every MCP-capable AI client (such as Claude Desktop or the Cursor editor) can use the updated functionality directly.</li>
</ul>
<h4 id="3-messy-security-and-permission-control">3. Messy Security and Permission Control<a aria-hidden="true" tabindex="-1" href="#3-messy-security-and-permission-control"><span class="anchor-link"> #</span></a></h4>
<ul>
<li><strong>Pain point:</strong> Authorizing AI usually means handing an API key to a third-party app, which is a security risk.</li>
<li><strong>Solution:</strong> MCP supports locally running servers. Your sensitive data (local code, financial reports, and so on) does not need to be uploaded to the cloud for processing; the MCP Server can run locally and give the model only the necessary summary information, preserving <strong>data ownership</strong>.</li>
</ul>
<h4 id="4-no-unified-tool-calling-standard">4. No Unified Tool Calling Standard<a aria-hidden="true" tabindex="-1" href="#4-no-unified-tool-calling-standard"><span class="anchor-link"> #</span></a></h4>
<ul>
<li><strong>Pain point:</strong> Function Calling formats differ slightly between models, so switching models often means rewriting tool logic.</li>
<li><strong>Solution:</strong> MCP defines unified interaction standards for Resources, Prompts (prompt templates), and Tools, making "model-driven tools" as simple and universal as calling a function.</li>
</ul>
<p>MCP is a revolution about "decoupling": it separates "what the model can do" from "how data is obtained".</p>
<p>Using an MCP server in LangChain is very simple, as shown below.</p>
<p><img src="/post/introtolangchainapp/002ee0df469e.png" alt="Using an MCP server in LangChain"></p>
<p>The example first starts a time-lookup MCP service, then has the agent fetch its tools and use them.</p>
<blockquote>
<p>For how to design and build an MCP service, see an MCP getting-started tutorial; the MCP protocol is documented <a href="https://modelcontextprotocol.io/docs/getting-started/intro">here</a>.</p>
</blockquote>
<h3 id="3-multi-agent-systems">3. Multi-Agent Systems<a aria-hidden="true" tabindex="-1" href="#3-multi-agent-systems"><span class="anchor-link"> #</span></a></h3>
<p>Why isn't a single agent enough?</p>
<p>In the demo stage, one agent often looks "smart enough", but once it hits real-world scenarios, the problems of a single agent surface quickly.</p>
<h4 id="1-problems-with-a-single-agent">1. Problems with a Single Agent<a aria-hidden="true" tabindex="-1" href="#1-problems-with-a-single-agent"><span class="anchor-link"> #</span></a></h4>
<p>These problems fall into several categories:</p>
<ul>
<li>
<p>Complex tasks make responsibilities spiral out of control</p>
<p>Understanding requirements, breaking down tasks, calling tools, and so on make the context grow longer and longer, so the reasoning path—and the result—becomes increasingly unpredictable.</p>
</li>
<li>
<p>Reasoning, execution, and verification are mixed together</p>
<p>With these three mixed, any error is very hard to pin down—the equivalent of a service with no clear responsibility boundaries in software engineering.</p>
</li>
<li>
<p>Very poor scalability and maintainability</p>
<p>For example, adding review capability or human intervention to the system may, with a single agent, mean rewriting the prompt and retesting every path, which is very risky.</p>
</li>
<li>
<p>Security and cost concerns</p>
<p>A single agent is a single service and may be granted high privileges it does not actually need. Those privileges are hard to narrow down, which puts pressure on both system security and cost.</p>
</li>
</ul>
<h4 id="2-designing-multiple-agents">2. Designing Multiple Agents<a aria-hidden="true" tabindex="-1" href="#2-designing-multiple-agents"><span class="anchor-link"> #</span></a></h4>
<p>The core idea of multi-agent design: <strong>split responsibilities instead of piling on capabilities</strong>.</p>
<p>Common multi-agent collaboration patterns include:</p>
<ul>
<li>
<p>Planner / Executor pattern</p>
<p>The Planner Agent understands the goal, breaks down the task, and produces an execution plan; the Executor Agent calls tools according to the plan and focuses on execution.</p>
</li>
<li>
<p>Reviewer / Worker pattern</p>
<p>The Reviewer Agent reviews task results, finds problems, provides revision suggestions, and decides whether to approve; the Worker Agent does the main work and produces the draft or result.</p>
</li>
<li>
<p>Manager / Sub-agent pattern</p>
<p>The Manager Agent analyzes the task type, decides which sub-agents to call, and aggregates the final result. Each Sub-agent handles one submodule or subdomain, with its own independent toolset and context.</p>
</li>
</ul>
<p>Below is an example of the Manager / Sub-agent pattern.</p>
<p>The example is an agent that supervises game players. When it detects a cheating player, it automatically sends a notification and bans the player in the system.</p>

<p><img src="/post/introtolangchainapp/0f5653456c0c.png" alt="Defining sub-agents"></p>
<p>Then define the Manager Agent (<code>main_agent</code> here).</p>
<p><img src="/post/introtolangchainapp/ac16add54f40.png" alt="Defining the manager agent"></p>
<p>Invoke the Manager Agent with the operation to perform; the result is shown below.</p>
<p><img src="/post/introtolangchainapp/9e3e46603903.png" alt="Multi-agent result"></p>
<p>In this pattern, the agent calls and their effects match expectations.</p>
<h2 id="4-toward-production-building-a-deployable-agent">4. Toward Production: Building a Deployable Agent<a aria-hidden="true" tabindex="-1" href="#4-toward-production-building-a-deployable-agent"><span class="anchor-link"> #</span></a></h2>
<p>Building an agent system is not just about getting it to run; what matters more is that it runs stably over the long term. This section covers what to pay attention to in production.</p>
<h3 id="1-introducing-agent-middleware">1. Introducing Agent Middleware<a aria-hidden="true" tabindex="-1" href="#1-introducing-agent-middleware"><span class="anchor-link"> #</span></a></h3>
<p>A traditional computer consists of a CPU, memory, and peripherals, and the operating system ties them together. By analogy, the LLM is the CPU, different agents are different applications, and Agent Middleware is the operating system of the agent system: it is the component that manages the different LLMs and agents. Without middleware, an agent system could only be managed by hand, which is tedious, hard to reuse, limited in extensibility, and error-prone. That is why Agent Middleware is the operating system of an agent system.</p>
<p>Agent Middleware usually falls into these categories:</p>
<ul>
<li>
<p>Runtime management</p>
<p>Addresses how agent steps advance and how to recover from failures.</p>
</li>
<li>
<p>Context and memory</p>
<p>Decides which information enters the context so the agent does not "forget", and how to compress context when it gets too long.</p>
</li>
<li>
<p>Tools and capabilities</p>
<p>Focuses on how tools are called safely and how to handle tool call failures.</p>
</li>
<li>
<p>Flow and collaboration</p>
<p>Concerns how multi-step tasks are broken down and how multiple agents collaborate.</p>
</li>
<li>
<p>Safety and governance</p>
<p>Covers agent security governance: agents must not act recklessly in the system, including intercepting risky operations to meet enterprise compliance requirements.</p>
</li>
<li>
<p>Observability and operations</p>
<p>Used for monitoring and debugging, making it easier to reproduce and fix errors and to track day-to-day metrics.</p>
</li>
</ul>

<h3 id="2-long-conversations-and-context-compression">2. Long Conversations and Context Compression<a aria-hidden="true" tabindex="-1" href="#2-long-conversations-and-context-compression"><span class="anchor-link"> #</span></a></h3>
<p>Long conversations and context compression are a very practical engineering problem that shows up as the number of turns grows. Overly long conversations consume a lot of tokens and drive up system cost. One approach is to forget useless information, such as intermediate tool-call results; a more common approach is to summarize the conversation history. The system then automatically condenses the history into a brief summary, so the agent does not lose its memory.</p>
<p>The example below shows how to use SummarizationMiddleware in LangChain to compress the context of a long conversation.</p>
<p>First, define an agent that supports short-term memory and uses the SummarizationMiddleware, then start asking questions.</p>

<p>After several rounds of Q&#x26;A, once the configured threshold is reached, the content in <code>messages</code> is compressed into a summary.</p>
<p><img src="/post/introtolangchainapp/fdaf729ba2f4.png" alt="Compressed messages after summarization"></p>

<h2 id="5-summary-and-next-steps">5. Summary and Next Steps<a aria-hidden="true" tabindex="-1" href="#5-summary-and-next-steps"><span class="anchor-link"> #</span></a></h2>
<p>First, an agent is not prompt engineering; it is systems engineering, and LangChain's role is to be the "glue" that builds that system.</p>
<p>Second, an agent is not always the best solution. For simple knowledge Q&#x26;A, you don't necessarily need an agent. For fixed-process scenarios, an agent may even disrupt an otherwise stable process and cause chaos.</p>
