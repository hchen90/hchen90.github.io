16:T4eb5,<p>When ChatGPT first took off, my workflow was: open a browser, paste a code snippet, wait for suggestions, then copy them back into the IDE by hand. That pattern is “chat-style assistance” — the AI talks, it does not act. What actually bends the productivity curve is the Agent: it does not just answer; it reads files, runs commands, edits code, and opens PRs. The catch is that dropping a large language model into an environment that can touch the filesystem is like handing a screwdriver to a child with no body awareness. It can fix things — or punch a hole through the motherboard.</p>
<p>The harness is the screwdriver’s “safety grip.” It is not the agent itself, but the middle layer between the agent and a real engineering environment: which tools the agent may call, what context it can see, how results are fed back, and how failures are contained. This post is about designing a dependable harness so agents join day-to-day development instead of becoming something you have to babysit.</p>
<h2 id="the-core-problem-agents-are-capable--how-do-you-let-them-touch-code-safely">The core problem: agents are capable — how do you let them touch code safely?<a aria-hidden="true" tabindex="-1" href="#the-core-problem-agents-are-capable--how-do-you-let-them-touch-code-safely"><span class="anchor-link"> #</span></a></h2>
<p>Agent capability boundaries are expanding fast. From early text completion, to GitHub Copilot’s inline suggestions, to systems like Cursor Composer and Pi Coding Agent that can edit across files, AI is shifting from “copilot” to “shift engineer.” Greater power means more concrete risk:</p>
<ul>
<li><strong>Hallucination-driven damage:</strong> an LLM may confidently delete code that looks “unused,” when it is actually a fallback for older versions.</li>
<li><strong>Excessive privileges:</strong> if the agent has shell and git access, one bad judgment can <code>git push --force</code> to main.</li>
<li><strong>Mismatched context:</strong> the agent never sees the CI failure logs, yet proposes fixes from stale local state.</li>
<li><strong>No audit trail:</strong> humans at least remember what they changed; an agent that ran twenty steps overnight leaves nobody sure what happened.</li>
</ul>
<p>In short: <strong>agents need engineering capabilities, but the engineering environment must not trust agents unconditionally.</strong> The harness is the protocol layer for that trust exchange.</p>
<h2 id="what-a-harness-is-more-than-tool-calling">What a harness is: more than “tool calling”<a aria-hidden="true" tabindex="-1" href="#what-a-harness-is-more-than-tool-calling"><span class="anchor-link"> #</span></a></h2>
<p>First, what a harness is <em>not</em>. OpenAI Function Calling, Anthropic Tool Use, and community MCP (Model Context Protocol) all essentially <strong>define a schema so the model learns when to call external functions</strong>. They answer “how does the model request tools?”</p>
<p>A harness answers <strong>who executes, how the environment is prepared, how safety is enforced, and how results are fed back</strong>. An analogy:</p>
<ul>
<li>Function Calling is the “restaurant menu” — it tells the model what it can order.</li>
<li>The harness is “kitchen + waiter + POS” — take the order, prep, cook, serve, handle returns.</li>
</ul>
<p>In systems like Pi Coding Agent, the harness usually shows up as a local daemon (or a process embedded in an IDE plugin). It exposes a set of <strong>capability declarations</strong> to the agent; the agent chooses what to call for the current task. When a request arrives, the harness does four things:</p>
<ol>
<li><strong>Discovery:</strong> tell the agent which tools exist in this environment. On a machine without Docker, do not expose <code>docker_build</code>.</li>
<li><strong>Context injection:</strong> pack the background the agent needs into the request. Do not dump the whole project tree; read relevant files, recent edits, and test-failure summaries on demand.</li>
<li><strong>Sandboxed execution:</strong> run commands or write files in a controlled environment — chroot, containers, or at least a whitelist check.</li>
<li><strong>Result feedback:</strong> return stdout, stderr, file diffs, and HTTP responses in a structured form, usually with metadata (exit code, duration, affected files).</li>
</ol>
<p>Function Calling and MCP are <strong>protocols</strong>; the harness is a <strong>runtime</strong>. They work together: the agent expresses intent via the protocol; the harness makes it real at runtime.</p>
<p><img src="/post/aiagentharness/1e4c509b3953.svg" alt="Harness architecture: the agent interacts with the engineering environment through the harness"></p>
<p><em>Figure: the harness sits in the middle — capabilities upward, controlled access to the filesystem, shell, and network downward.</em></p>

<p>This skeleton runs, but production will hit pitfalls immediately:</p>
<ul>
<li><strong>Path escape:</strong> <code>../etc/passwd</code> is blocked by <code>startsWith</code>, but symlinks can bypass it. Safer: <code>realpath</code> first, then compare.</li>
<li><strong>Command injection:</strong> splitting on spaces is wrong. Spaces in <code>git log --format="%H %s"</code> shatter arguments. Pass argv as an array (<code>execFile</code>, not <code>exec</code>).</li>
<li><strong>Concurrent write races:</strong> two agent threads editing the same file — last write wins. Lock files or serialize writes.</li>
<li><strong>Uncontrolled side effects:</strong> <code>npm install</code> mutates <code>node_modules</code>; without snapshots, rollback is a heavy <code>git checkout .</code>.</li>
</ul>
<h2 id="context-windows-and-designing-the-tool-protocol">Context windows and designing the “tool protocol”<a aria-hidden="true" tabindex="-1" href="#context-windows-and-designing-the-tool-protocol"><span class="anchor-link"> #</span></a></h2>
<p>Every agent decision depends on the context the harness feeds it. Too much wastes tokens; too little and the agent guesses. One harness job is to be an <strong>information curator</strong>.</p>
<p>For fixing a bug, an ideal information flow looks like:</p>
<table>
<thead>
<tr>
<th>Stage</th>
<th>Context the harness provides</th>
<th>Why not everything</th>
</tr>
</thead>
<tbody>
<tr>
<td>Locate</td>
<td>Error stack + related paths</td>
<td>Not the whole-repo AST</td>
</tr>
<tr>
<td>Understand</td>
<td>Source of the failing function and its call chain</td>
<td>Not <code>node_modules</code></td>
</tr>
<tr>
<td>Fix</td>
<td>Full target file + dependent interface signatures</td>
<td>Not every test file</td>
</tr>
<tr>
<td>Verify</td>
<td>Test command output (failed-case summary)</td>
<td>Not the full CI log</td>
</tr>
</tbody>
</table>
<p>Harnesses usually implement this layering with a few mechanisms:</p>
<p><strong>1. Symbol index</strong>
Prebuild file → symbol → reference indexes (Tree-sitter or LSP). When the agent mentions <code>UserService.authenticate</code>, the harness finds definitions and call sites quickly instead of grepping the whole repo.</p>
<p><strong>2. Prefer recent changes</strong>
Files the agent just edited, open editor tabs, and recent git diffs are “hot” — inject them first.</p>
<p><strong>3. Structured summaries</strong>
Do not shove a 10 MB log at the agent. Preprocess: extract error lines, dedupe stacks, count failures, then emit a short structured summary:</p>

<p><strong>4. Dynamic context protocol</strong>
Agree on pull-on-demand: the agent gets a skeleton, notices a missing interface, then explicitly requests <code>read_symbol("PaymentGateway.charge")</code>. More controllable than dumping everything once.</p>
<p>The point: <strong>the harness understands the engineering structure better than the agent, so the harness should decide what is worth seeing</strong> — not let the agent rummage the repo.</p>
<h2 id="safety-boundaries-least-privilege-and-auditability">Safety boundaries: least privilege and auditability<a aria-hidden="true" tabindex="-1" href="#safety-boundaries-least-privilege-and-auditability"><span class="anchor-link"> #</span></a></h2>
<p>Path escape and command injection are only the start. Harness security is defense in depth:</p>
<p><strong>1. Filesystem sandbox</strong>
Lightweight: <code>chroot</code> or bind-mount the agent into the project directory. More modern: run the harness in a container (e.g. Docker rootless) with read-only mounts. Default <strong>deny</strong>: writing a file requires a whitelist pass.</p>
<p><strong>2. Command whitelist and argument checks</strong>
Validate more than the binary name — validate argument patterns. Allow <code>git diff</code>, not <code>git push</code>; allow <code>npm test</code>, not <code>npm publish</code>. Regex or templates work:</p>

Agents should not freely hit the public internet. Some tasks need it (npm package versions). Maintain an allowlist (registry.npmjs.org, pypi.org); block the rest by default. If search is needed, the harness proxies and returns redacted results.</p>

<p>With an audit log you can answer “what did the agent change?” Further: require human confirmation before sensitive ops (<code>git push</code>, <code>rm -rf</code>), keeping autonomy at the “suggest” layer rather than “execute.”</p>
<p><strong>5. Rollback</strong>
If the agent breaks the tree, stash or branch before each write. After a multi-step failure, roll back to the start in one shot instead of manually checking out twenty files.</p>
<h2 id="wrap-up">Wrap-up<a aria-hidden="true" tabindex="-1" href="#wrap-up"><span class="anchor-link"> #</span></a></h2>
<p>Wiring AI agents into engineering workflows is not only about better models — you need a reliable harness as the safety grip. Core points:</p>
<ol>
<li><strong>The harness is a runtime, not a protocol.</strong> Function Calling / MCP define how agents express intent; the harness executes safely in the real environment and feeds results back.</li>
<li><strong>Context should be curated by the harness.</strong> Agents should not rummage the repo; the harness injects symbols, summaries, and dynamic data by stage, balancing token cost and precision.</li>
<li><strong>Safety is default-deny plus auditability.</strong> Sandboxes, allowlists, and network isolation are baseline; operation logs and rollback are what make people willing to put agents near CI.</li>
</ol>
