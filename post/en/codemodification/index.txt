16:T78c3,<h1 id="what-is-a-code-change">What Is a Code Change<a aria-hidden="true" tabindex="-1" href="#what-is-a-code-change"><span class="anchor-link"> #</span></a></h1>
<p>Every software project has a lifecycle, and however long or short it is, it involves code changes. Whether you are fixing earlier defects or iterating on each story in agile development, code modifications happen to some degree.</p>
<h1 id="why-code-changes-happen">Why Code Changes Happen<a aria-hidden="true" tabindex="-1" href="#why-code-changes-happen"><span class="anchor-link"> #</span></a></h1>
<p>Code changes are very common, yet they are something we should try to avoid. Think in extremes. At one end is code so universally compatible that it meets business needs without any modification. Such code does exist in practice: if you treat business code not as real code but as business logic flow, then in a script-driven service framework the foundation is written in an efficient native language (for example C++) using general design models and abstractions. That foundation rarely changes, and the business scripts on top are driven by it, so this code almost never needs modification—only the business scripts do (no-code solutions are another form of this extreme thinking). At the other end is the opposite: business logic is scattered into every corner of the code with hardly any abstraction layer. If you are not familiar with the business, such code is hard to read; every business change directly triggers a code change, and both maintainability and reusability are low.</p>
<blockquote>
<p>None of us want to modify code, because changes cost money, time, and effort—and we do it merely to make up for earlier shortcomings? So why not think ahead for the later stages from the start and do preventive work? It is better for the project's health and lowers maintenance costs down the line.</p>
</blockquote>
<h1 id="how-to-make-code-changes">How to Make Code Changes<a aria-hidden="true" tabindex="-1" href="#how-to-make-code-changes"><span class="anchor-link"> #</span></a></h1>
<p>We can try to avoid changing code, but sometimes we have to. So making changes well and reducing their shortcomings also improves the quality of the project's code.</p>
<p>How to write elegant code has always been well documented; the computing industry has a wealth of material on it.</p>
<h2 id="common-sense-rules-for-code">Common-Sense Rules for Code<a aria-hidden="true" tabindex="-1" href="#common-sense-rules-for-code"><span class="anchor-link"> #</span></a></h2>
<p>Most people know the common-sense rules. They don't matter to the code's logic, since they have nothing to do with the code itself, but following them reduces mistakes.</p>
<h3 id="code-alignment">Code Alignment<a aria-hidden="true" tabindex="-1" href="#code-alignment"><span class="anchor-link"> #</span></a></h3>
<p>Generally, using spaces instead of tabs noticeably improves this, especially in team development (with advanced editors that format code automatically, alignment is hardly something you need to worry about).</p>
<h3 id="code-comments">Code Comments<a aria-hidden="true" tabindex="-1" href="#code-comments"><span class="anchor-link"> #</span></a></h3>
<p>Comments are also part of code formatting. Sensible comments help developers understand the code and work more efficiently. Today there are all kinds of comment formats, some of which generate rich API documentation, and so on—all to make the code easier to read and understand later.</p>
<h2 id="what-to-watch-for-in-code-logic">What to Watch for in Code Logic<a aria-hidden="true" tabindex="-1" href="#what-to-watch-for-in-code-logic"><span class="anchor-link"> #</span></a></h2>
<p>When it comes to logic flow, code written by different people with different habits can differ enormously, but plenty of good logic patterns are worth learning from. Unlike the formatting rules above, logic flow directly affects how well the compiled code runs.</p>

<h3 id="duplicate-code-blocks">Duplicate Code Blocks<a aria-hidden="true" tabindex="-1" href="#duplicate-code-blocks"><span class="anchor-link"> #</span></a></h3>
<p>Sometimes code contains several small snippets that do nearly the same thing (quite possibly left behind by someone's Ctrl+C / Ctrl+V and tweaks) and are used frequently. Such code can be further refactored into a single reusable function.</p>
<h3 id="tracking-execution-with-state-flags">Tracking Execution with State Flags<a aria-hidden="true" tabindex="-1" href="#tracking-execution-with-state-flags"><span class="anchor-link"> #</span></a></h3>
<p>State flags are really the State pattern design described above (used for deterministic for loops). In fact, the State pattern is not just for loops—it can be used anywhere. For complex execution flows, though, the State pattern makes the flow easier to abstract and easier to debug and troubleshoot. Its benefits are obvious, which is why many well-designed architectures choose it for handling complex flows.</p>
<h1 id="code-philosophy">Code Philosophy<a aria-hidden="true" tabindex="-1" href="#code-philosophy"><span class="anchor-link"> #</span></a></h1>
<p>As far as code goes, if it satisfies the following, it can be called excellent code:</p>
<ul>
<li>Passes all tests</li>
<li>Contains no duplicate code</li>
<li>Expresses all of the system's design ideas</li>
<li>Contains as few entities as possible (for example, types and functions)</li>
</ul>
<h2 id="naming-conventions">Naming Conventions<a aria-hidden="true" tabindex="-1" href="#naming-conventions"><span class="anchor-link"> #</span></a></h2>
<ul>
<li>snake_case</li>
<li>UpperCamelCase (PascalCase)</li>
<li>lowerCamelCase</li>
</ul>
<p>A consistent variable naming convention makes code easier to discuss and understand, which improves team productivity.</p>
<h2 id="code-formatting">Code Formatting<a aria-hidden="true" tabindex="-1" href="#code-formatting"><span class="anchor-link"> #</span></a></h2>
<p>Code formatting is mainly about the conventions or defaults for whitespace, line breaks, and the like. Editors can usually be customized for these, and the team can share one coding standard so that the same project does not end up with different display styles due to inconsistent formatting.</p>
<h2 id="code-abstraction">Code Abstraction<a aria-hidden="true" tabindex="-1" href="#code-abstraction"><span class="anchor-link"> #</span></a></h2>
<p>Code abstraction deserves some discussion. In software engineering you must understand design patterns—not by memorizing every pattern, but by understanding the common ones and knowing when to use them and what problems they solve.</p>
<h3 id="why-use-design-patterns">Why Use Design Patterns?<a aria-hidden="true" tabindex="-1" href="#why-use-design-patterns"><span class="anchor-link"> #</span></a></h3>
<p>When solving the same problem, different people may express it in different ways, and the differences become even more visible at the code level. In a team project, such code may be maintained by dozens of people at once, and having each of them untangle its specific logic costs a lot of time and effort. So why not let the team communicate in a common language? That is why design patterns exist at the logical level. If Zhang San writes logic that expresses the <strong>Facade pattern</strong>, Li Si only needs to know the <strong>Facade pattern</strong> to understand the logic at a glance after reading the code. The team saves a great deal of time and effort and can put that energy into more meaningful work.</p>
<p>Design patterns are the common underlying logic of application software development, so the first thing a developer needs to do is abstract functional logic into design patterns (if you can't, it generally means you haven't mastered design patterns).</p>
<blockquote>
<p>The Law of Demeter:
A module's users should not know the internal details of the objects it uses.</p>
</blockquote>
<h2 id="unit-testing">Unit Testing<a aria-hidden="true" tabindex="-1" href="#unit-testing"><span class="anchor-link"> #</span></a></h2>
<p>Unit testing is a tool for verifying the correctness of functional modules in code. If all of the software's modules are correct, the integrated code is easy to debug and very likely correct too. Functional modules are a local problem, while integrated software is a global one. If the global behavior is wrong, it means there are errors in the order or interdependencies of the parts, so we don't need to look inside the modules again—we only need to adjust the order or dependencies between modules to fix the problem.</p>
<h2 id="rules-of-emergent-design">Rules of Emergent Design<a aria-hidden="true" tabindex="-1" href="#rules-of-emergent-design"><span class="anchor-link"> #</span></a></h2>
<ul>
<li>Pass all tests</li>
<li>Refactor the code</li>
<li>No duplicate code</li>
<li>Express the programmer's intent</li>
<li>Minimize the number of classes and methods</li>
</ul>
<h2 id="concurrency">Concurrency<a aria-hidden="true" tabindex="-1" href="#concurrency"><span class="anchor-link"> #</span></a></h2>
<p>In multithreaded systems, concurrency problems arise. Concurrency means that the timing of multiple execution nodes' use of a resource is nondeterministic.</p>
<blockquote>
<p>Concurrency vs. parallelism:
Concurrency means the timing of multiple execution nodes' use of a single resource is nondeterministic—you cannot tell who goes first. Parallelism means multiple execution nodes may use a single resource at the same time.
In practice, solving concurrency problems well also solves parallelism problems.</p>
</blockquote>
<h3 id="mutual-exclusion-and-synchronization">Mutual Exclusion and Synchronization<a aria-hidden="true" tabindex="-1" href="#mutual-exclusion-and-synchronization"><span class="anchor-link"> #</span></a></h3>
<p>Precisely because the timing of multiple execution nodes' use of a single resource is nondeterministic, we need a mechanism for mutually exclusive, synchronized use.</p>
<p>First, there is mutual exclusion. It is an exclusive operation: while a resource is in use, it is locked, and other users cannot acquire it.</p>
<p>Operating systems express this with P and V operations:</p>
<div class="code-block-wrapper"><div class="code-block-header"><span class="code-block-lang">scss</span><button class="copy-button" data-copy-state="copy" aria-label="Copy code to clipboard" type="button" onclick="copyCode(this)"><span class="copy-button-text">Copy</span></button></div><pre><code class="hljs language-scss">  <span class="hljs-selector-tag">P</span>()
  <span class="hljs-built_in">do_resource</span>()
  <span class="hljs-built_in">V</span>()
</code></pre></div>
<p>P and V are both atomic. After P is executed, if the resource is already in use, P blocks until the resource is free. Once V executes, the resource is released, and one user blocked on P immediately gains access and continues the acquire/use/release cycle.</p>
<p>C++ uses the same mechanism:</p>
<div class="code-block-wrapper"><div class="code-block-header"><span class="code-block-lang">cpp</span><button class="copy-button" data-copy-state="copy" aria-label="Copy code to clipboard" type="button" onclick="copyCode(this)"><span class="copy-button-text">Copy</span></button></div><pre><code class="hljs language-cpp"><span class="hljs-type">static</span> std::unordered_map&#x3C;std::string> resource;

  mut.<span class="hljs-built_in">lock</span>();
  <span class="hljs-built_in">consume</span>(&#x26;resource);

<p>C++ also allows a kind of atomic lock (spin lock), suitable when the resource is held for a bounded time. It works by making threads wait so that only one thread consumes the resource at a time. It fits logic where resource consumption is brief, and because of its simple structure it is often more efficient than a mutex.</p>
<div class="code-block-wrapper"><div class="code-block-header"><span class="code-block-lang">cpp</span><button class="copy-button" data-copy-state="copy" aria-label="Copy code to clipboard" type="button" onclick="copyCode(this)"><span class="copy-button-text">Copy</span></button></div><pre><code class="hljs language-cpp"><span class="hljs-type">static</span> <span class="hljs-type">int</span> lck = <span class="hljs-number">0</span>;

<p>Synchronization is derived from mutual exclusion: it is the problem of synchronizing two mutually exclusive operations. Again, it is expressed with P and V.</p>

<h3 id="the-producerconsumer-concept">The Producer–Consumer Concept<a aria-hidden="true" tabindex="-1" href="#the-producerconsumer-concept"><span class="anchor-link"> #</span></a></h3>
<p>Producer and consumer are an abstraction of the mutual exclusion and synchronization problem, with a more general way of taking and using resources—usually a resource container pool. As long as producers have not filled the pool, they can keep storing resources; consumers can keep consuming until the pool is empty. This makes mutual exclusion and synchronization more efficient.</p>
<p>In C++, the producer and consumer can be expressed like this:</p>
<div class="code-block-wrapper"><div class="code-block-header"><span class="code-block-lang">cpp</span><button class="copy-button" data-copy-state="copy" aria-label="Copy code to clipboard" type="button" onclick="copyCode(this)"><span class="copy-button-text">Copy</span></button></div><pre><code class="hljs language-cpp"><span class="hljs-type">static</span> std::mutex producer_lock;

<span class="hljs-type">static</span> std::unordered_map&#x3C;std::string> poll;

  producer_lock.<span class="hljs-built_in">lock</span>();

  poll_lock.<span class="hljs-built_in">unlock</span>();
