16:T108c,<p>Software design patterns are a basic problem-solving method in software engineering: they provide a reasonable sequence of steps for reaching a goal. This post briefly covers why we need them, what they do, and their main building blocks.</p>
<h2 id="what-is-a-software-design-pattern">What Is a Software Design Pattern<a aria-hidden="true" tabindex="-1" href="#what-is-a-software-design-pattern"><span class="anchor-link"> #</span></a></h2>
<p>A software design pattern is, in essence, an abstract, well-reasoned set of steps for reaching a goal, defined in order to solve a problem.</p>
<p>Which pattern to use depends on the specific business scenario; each pattern has its own intent, motivation, and structure.</p>
<blockquote>
<p>Who invented design patterns</p>
<blockquote>
<p>The concept of patterns comes from architecture and was first proposed by Christopher Alexander. It was later applied to software development to address various problems in program design, with the Gang of Four (GoF) book as its earliest landmark. Since the end of the last century, the approach has been everywhere in medium and large software design and has become a common reference standard.</p>
</blockquote>
</blockquote>
<h2 id="why-we-need-software-design-patterns">Why We Need Software Design Patterns<a aria-hidden="true" tabindex="-1" href="#why-we-need-software-design-patterns"><span class="anchor-link"> #</span></a></h2>
<p>Software design patterns are a toolbox for solving problems, which is especially important in object-oriented problem settings.</p>
<p>Design patterns are also a shared language for communication. Imagine a colleague writes a large module in a purely procedural, function-by-function style, and the module now has to be handed over to someone else for maintenance. The new owner may face misunderstandings and other unknown risks (the proverbial "spaghetti code" mess). People understand structured, visual things more easily, and design patterns are a general methodology in that sense.</p>
<blockquote>
<p>Some things to watch out for</p>
<blockquote>
<p>Design patterns have many benefits, but they are not without drawbacks. The most common problem is misuse: some modern high-level languages offer better solutions that can replace a classic pattern. Another is overuse: a pattern only shows its value when it brings a meaningful improvement to the project. For example, in some business scenarios you can use the Facade pattern to provide a uniform interface and hide internal system complexity, but if the system's internals are not complex to begin with, there is no need to do so.</p>
</blockquote>
</blockquote>
<h2 id="what-design-patterns-are-there">What Design Patterns Are There<a aria-hidden="true" tabindex="-1" href="#what-design-patterns-are-there"><span class="anchor-link"> #</span></a></h2>
<p>Design patterns fall into three main categories:</p>
<ul>
<li>Creational Patterns</li>
<li>Structural Patterns</li>
<li>Behavioral Patterns</li>
</ul>
<p>Their relationships are shown below:</p>
<p><img src="/post/softwaredesignpattern1/61b6ed2bec38.png" alt="Design Pattern"></p>
<h3 id="creational-patterns">Creational Patterns<a aria-hidden="true" tabindex="-1" href="#creational-patterns"><span class="anchor-link"> #</span></a></h3>
<p>Creational patterns deal with object construction and improve code flexibility and reusability. Common ones include:
Factory Method, Abstract Factory, Builder, Prototype, and Singleton.</p>
<h3 id="structural-patterns">Structural Patterns<a aria-hidden="true" tabindex="-1" href="#structural-patterns"><span class="anchor-link"> #</span></a></h3>
<p>Structural patterns describe how objects and data structures are assembled and composed. Common ones include:
Adapter, Bridge, Composite, Decorator, Facade, Flyweight, and Proxy.</p>
