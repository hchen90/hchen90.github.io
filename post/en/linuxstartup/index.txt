16:T4fa2,<h1 id="loading-the-kernel">Loading the kernel<a aria-hidden="true" tabindex="-1" href="#loading-the-kernel"><span class="anchor-link"> #</span></a></h1>
<p>In the <a href="/post/en/systemstartup">previous post</a> I explained how computers boot, from early machines to modern ones, but I did not go deeper once we reached the operating system layer. In this post I use Linux as an example to describe how an operating system boots.</p>
<p>Kernel files are usually kept in the system's <code>/boot</code> directory, for example:</p>
<div class="code-block-wrapper"><div class="code-block-header"><span class="code-block-lang">shell</span><button class="copy-button" data-copy-state="copy" aria-label="Copy code to clipboard" type="button" onclick="copyCode(this)"><span class="copy-button-text">Copy</span></button></div><pre><code class="hljs language-shell">initramfs-linux.img
vmlinuz-linux
</code></pre></div>
<p>When GRUB (or LILO) loads the kernel, it maps <code>vmlinuz-linux</code> into memory and also loads an initial root filesystem image (<code>initramfs-linux.img</code>) into memory as a filesystem. The system boots from this mini initial filesystem, which in turn mounts the real on-disk filesystem. Every setup with an <code>initramfs</code> follows this flow. For systems without an <code>initramfs</code> (for example, the Slackware distribution), the kernel loads the filesystem directly from disk after it starts. Which path is used depends on the kernel configuration.</p>
<blockquote>
<p>What does kernel initialization do?</p>
<p>Kernel initialization belongs to OS kernel internals. Broadly, the main parts are the following (for the many details, see books on the Linux kernel):</p>
<ul>
<li>The system starts in real mode and must switch to protected mode, so it sets up the GDT and LDT and configures flat-mode memory addressing; the GDT/LDT entries can specify memory protection bits, sizes, and similar information</li>
<li>The bare system has no libraries to use, but don't forget the interrupt calls provided by the BIOS and the various I/O ports the BIOS has configured. Through them we can read and set hardware information and thus control the machine. We can wrap them into function calls; for historical compatibility some low interrupts must be preserved, so these functions are exposed as interrupt calls (i.e. by setting up the IDT, the interrupt descriptor table), providing a set of SYSCALLs following UNIX conventions</li>
<li>In practice, computer memory is already very large, so we need a mechanism for fast address lookup. Without hardware support, software algorithms can achieve something similar, but the Intel platform provides Paging: we only need to set up the PDE tables (page tables), and the CPU performs the address translation automatically, which effectively gives hardware acceleration</li>
<li>Once process-related and memory-related setup is done, next comes the filesystem, a fundamental element of the operating system (at least for now). The kernel reads file information according to the on-disk data format and builds in-memory data structures describing the files (usually not a simple bitmap-like table; in most cases it is more complex, i.e. a multi-level, extensible tree structure)</li>
<li>Peripherals are the most complex part. They need various kinds of initialization before they can be used normally; this is generally called the device driver flow (this part can also be deferred and initialized later)</li>
</ul>
</blockquote>
<h1 id="loading-the-init-program">Loading the init program<a aria-hidden="true" tabindex="-1" href="#loading-the-init-program"><span class="anchor-link"> #</span></a></h1>
<p>Once the kernel has finished loading (which it will, as long as no error occurs), it starts the system's first process: the famous <code>init</code> process (PID 1). With the growth of the open-source community there have been many versions of init. The oldest and most stable is sysvinit; there are also alternatives such as Upstart, but systemd is the most favored, and it is currently the most actively developed open-source init project.</p>
<p>Systemd and sysvinit differ a lot, so I'll introduce them separately:</p>
<blockquote>
<p>Upstart is an asynchronous, event-driven init system that is highly compatible with sysvinit, but it is not covered here; see other blogs or technical wikis about Upstart.</p>
</blockquote>
<h2 id="the-sysvinit-flow">The sysvinit flow<a aria-hidden="true" tabindex="-1" href="#the-sysvinit-flow"><span class="anchor-link"> #</span></a></h2>
<p>Sysvinit startup can be viewed as two parts: initialization and service loading.</p>
<h3 id="initialization">Initialization<a aria-hidden="true" tabindex="-1" href="#initialization"><span class="anchor-link"> #</span></a></h3>
<p>Sysvinit reads <code>/etc/inittab</code> to decide what the system should do next. To decide the next step, there is a concept called the "runlevel", which determines the scenario the system boots into. Generally, Linux has the following 7 runlevels:</p>
<ul>
<li>0 - halt</li>
<li>1 - single-user mode</li>
<li>2 - multi-user mode</li>
<li>3 - multi-user mode with networking</li>
<li>4 - user-defined</li>
<li>5 - full mode</li>
<li>6 - reboot</li>
</ul>
<blockquote>
<p>For the definition of runlevels, see <a href="https://en.wikipedia.org/wiki/Runlevel">Wikipedia</a>.</p>
</blockquote>
<p>The values above are not necessarily the same across Linux distributions.</p>
<p>The init program reads <code>/etc/inittab</code>, which stores what to do for each runlevel. Suppose the configuration is:</p>

<li>Mounting <code>tmpfs</code></li>
<li>Mounting the <code>proc</code> filesystem</li>

<p>This is how the system loads the initialization scripts under rc.d, completing the entire init process sequentially.</p>
<h3 id="loading-services">Loading services<a aria-hidden="true" tabindex="-1" href="#loading-services"><span class="anchor-link"> #</span></a></h3>
<p>In sysvinit, services are loaded by the initialization scripts under <code>/etc/rc.d</code>. Usually each service has its own Shell management script that accepts arguments such as <code>status</code>, <code>start</code>, <code>stop</code>, and <code>restart</code>, placed under <code>/etc/rc.d/init.d</code>.</p>
<p>For example, given a service (<code>/etc/rc.d/init.d/vbox-usb-service</code>), we can run:</p>

<p>starts the httpd service.</p>
<blockquote>
<p>Third-party services go under <code>/etc/rc.d/init.d</code>; as long as these scripts are made executable, the initialization scripts load them automatically, with no need to modify the init scripts. The management scripts directly under <code>/etc/rc.d</code> are services shipped with the Linux distribution, which the init scripts already check for. If you want to put a third-party service script under <code>/etc/rc.d</code>, you must modify the init scripts.</p>
</blockquote>
<h2 id="the-systemd-flow">The systemd flow<a aria-hidden="true" tabindex="-1" href="#the-systemd-flow"><span class="anchor-link"> #</span></a></h2>
<p>In systemd, everything is loaded as units. Many of these units can run concurrently to speed up booting, and each unit's predecessors and successors form a stable loading system.</p>
<h3 id="initialization-1">Initialization<a aria-hidden="true" tabindex="-1" href="#initialization-1"><span class="anchor-link"> #</span></a></h3>
<blockquote>
<p>On a Linux system using systemd as init, see <code>man 7 bootup</code> for more details on how systemd boots.</p>
</blockquote>
<h3 id="loading-diagram">Loading diagram<a aria-hidden="true" tabindex="-1" href="#loading-diagram"><span class="anchor-link"> #</span></a></h3>
<p><img src="/post/linuxstartup/5825be82891a.png" alt="systemd boot graph"></p>
<p>As the diagram shows, many services can be loaded before <code>sysinit</code>. These services are independent with no dependencies on each other, so they can be loaded in parallel. Once all of them have loaded, the <code>sysinit</code> target is considered complete, and loading moves on to the next services, and so on. Note that units like <code>rescue</code> serve special purposes (here, rescuing the system after a crash), and there are also services with an independent dependency chain, or no dependencies, that get pulled into the current stage, such as <code>remote-fs</code> in the diagram.</p>
<blockquote>
<p>The systemd diagram above is rather rough; the real details are more complex. Some units load in several steps, and some break down into even finer-grained loading logic.</p>
</blockquote>
<h1 id="user-login">User login<a aria-hidden="true" tabindex="-1" href="#user-login"><span class="anchor-link"> #</span></a></h1>
<p>After the necessary system services have started, there are several scenarios:</p>
<h2 id="runlevel-3-login">Runlevel 3 login<a aria-hidden="true" tabindex="-1" href="#runlevel-3-login"><span class="anchor-link"> #</span></a></h2>
<p>In this mode, the user logs in on a text console. init starts <code>/sbin/agetty</code> to prompt for a username and password; once getty and login verify the user, the user is let into the system and their Shell is started.</p>
<blockquote>
<p>The configuration above allows 6 users to be logged in at the same time.</p>
<p>In addition, getty and login need to verify the password, usually by reading the stored settings under <code>/etc/passwd</code> to validate the user.</p>
<p>(For details, see the system function <code>getpass</code>.)</p>
</blockquote>
<h2 id="runlevel-4-login">Runlevel 4 login<a aria-hidden="true" tabindex="-1" href="#runlevel-4-login"><span class="anchor-link"> #</span></a></h2>
<p>In multi-user graphical mode, a service that manages system logins is started (PolKit/ConsoleKit are the most common). Taking ConsoleKit as an example: it lets a user log in again on the same hardware without logging out first. ConsoleKit abstracts logins into a session model to achieve this.</p>
<p>Graphical logins all work this way.</p>
<blockquote>
<p>Under ConsoleKit, user validation is likewise done by reading the information in the <code>/etc/passwd</code> configuration file.</p>
<p>(For details on how verification works, see the security-related system function <code>crypt</code>.)</p>
</blockquote>
<h1 id="launching-the-users-shell--wdm">Launching the user's Shell / WDM<a aria-hidden="true" tabindex="-1" href="#launching-the-users-shell--wdm"><span class="anchor-link"> #</span></a></h1>
<p>Once the user enters a name and password that pass verification, init needs to run a Shell for the user so they can manage the system. There are many kinds of Shell, and users can freely choose one that suits their taste.</p>
<blockquote>
<p>Common Shells include: Bash, Csh, Ash, Tcsh, Zsh, and so on</p>
</blockquote>
<p>Once the Shell starts, it takes over the user's space, and the user can do anything through it via commands.</p>
<blockquote>
<p>When a Shell starts, it reads the system-wide configuration, then reads the user's custom configuration from files under the user's $HOME directory.</p>
</blockquote>
<p>Graphical logins are a bit different: instead of a Shell, they start an X Window WDM, i.e. a window/display manager, which takes over the user's space, initializes the graphical settings for the user, and displays the graphical interface.</p>

<p>Common WDMs include: GDM, SDDM, KDM, and so on</p>
