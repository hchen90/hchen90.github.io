15:T4fa9,<p>ChatGPT 刚火起来的时候，我的使用方式是打开浏览器，把代码片段贴进去，等它给建议，再手动复制回 IDE。这种模式叫「聊天式辅助」—— AI 只管说，不动手。真正改变效率曲线的是 Agent：它不只是给答案，而是直接读文件、跑命令、改代码、提交 PR。问题是，把一个大语言模型放进能操作文件系统的环境里，相当于给一个没有身体感知的小孩一把螺丝刀。它可以修东西，也可以把主板捅穿。</p>
<p>Harness 就是这把螺丝刀的「安全手柄」。它不是 Agent 本身，而是 Agent 与真实工程环境之间的中间层：决定 Agent 能调用哪些工具、能看到什么上下文、执行结果如何回传，以及出了错怎么兜底。本文想聊的是，怎么设计一个靠谱的 Harness，让 Agent 真正融入日常开发，而不是成为需要人盯着的麻烦。</p>
<h2 id="核心问题agent-能力很好但怎么让它安全地操作代码">核心问题：Agent 能力很好，但怎么让它安全地操作代码？<a aria-hidden="true" tabindex="-1" href="#核心问题agent-能力很好但怎么让它安全地操作代码"><span class="anchor-link"> #</span></a></h2>
<p>Agent 的能力边界在快速扩展。从早期的文本补全，到 GitHub Copilot 的 inline suggestion，再到 Cursor Composer、Pi Coding Agent 这类能跨文件改代码的系统，AI 正在从「副驾驶」变成「轮班工程师」。但能力越大，风险越具体：</p>
<ul>
<li><strong>幻觉导致破坏</strong>：LLM 可能自信地删除看起来「没用」的代码，而那恰好是兼容旧版本的 fallback。</li>
<li><strong>权限过大</strong>：如果 Agent 拿到了 shell 和 git 权限，一次误判就能 <code>git push --force</code> 到主分支。</li>
<li><strong>上下文错配</strong>：Agent 看不到 CI 失败日志，却基于过时的本地状态给出修复建议。</li>
<li><strong>不可审计</strong>：手动操作至少有人记得改了什么，Agent 半夜跑了 20 个步骤，第二天没人说得清。</li>
</ul>
<p>一句话：<strong>Agent 需要工程环境的能力，但工程环境不能毫无保留地信任 Agent。</strong> Harness 就是这个信任交换的协议层。</p>
<h2 id="harness-是什么不只是工具调用">Harness 是什么：不只是「工具调用」<a aria-hidden="true" tabindex="-1" href="#harness-是什么不只是工具调用"><span class="anchor-link"> #</span></a></h2>
<p>先说清楚 Harness 不是什么。OpenAI 的 Function Calling、Anthropic 的 Tool Use、以及社区里的 MCP（Model Context Protocol），本质都是<strong>定义一套 Schema，让模型学会在什么时候调用外部函数</strong>。它们解决的是「模型怎么请求工具」的问题。</p>
<p>Harness 解决的是<strong>谁来执行、怎么准备环境、怎么保证安全、怎么把结果喂回去</strong>的问题。打个比方：</p>
<ul>
<li>Function Calling 是「餐厅菜单」—— 告诉模型有哪些菜可以点。</li>
<li>Harness 是「后厨 + 服务员 + 收银系统」—— 接单、备料、烹饪、上菜、处理退单。</li>
</ul>
<p>在 Pi Coding Agent 这类系统里，Harness 通常表现为一个本地守护进程（或者嵌入在 IDE 插件里的进程）。它向 Agent 暴露一组<strong>能力声明</strong>（Capabilities），Agent 根据当前任务选择调用。Harness 收到请求后，做四件事：</p>
<ol>
<li><strong>能力发现（Discovery）</strong>：告诉 Agent 当前环境有哪些工具可用。比如在一个没有 Docker 的机器上，就不应该暴露 <code>docker_build</code> 这个工具。</li>
<li><strong>上下文注入（Context Injection）</strong>：把 Agent 需要的背景信息打包进请求。不是把整个项目目录 dump 过去，而是按需读取相关文件、最近修改、测试失败摘要。</li>
<li><strong>执行沙箱（Sandboxed Execution）</strong>：在受控环境里跑命令或写文件。沙箱可以是 chroot、容器、或者最简单的白名单校验。</li>
<li><strong>结果回传（Result Feedback）</strong>：把 stdout、stderr、文件 diff、HTTP 响应格式化后返回给 Agent，通常附带结构化的元数据（退出码、耗时、影响文件列表）。</li>
</ol>
<p>Function Calling 和 MCP 是<strong>协议</strong>，Harness 是<strong>运行时</strong>。两者配合：Agent 用协议表达意图，Harness 在运行时把它落地。</p>
<p><img src="/post/aiagentharness/1e4c509b3953.svg" alt="Harness 架构：Agent 通过 Harness 与工程环境交互"></p>
<p><em>图：Harness 作为中间层，向上暴露能力声明，向下管控对文件系统、Shell 和网络的访问。</em></p>

<p>这个骨架能跑，但生产环境马上会踩坑：</p>
<ul>
<li><strong>路径逃逸</strong>：<code>../etc/passwd</code> 被 <code>startsWith</code> 挡住，但符号链接可以绕过去。稳妥做法是先 <code>realpath</code> 再比较。</li>
<li><strong>命令注入</strong>：上面用 <code>split(' ')</code> 解析命令是错的。<code>git log --format="%H %s"</code> 里的空格会把参数切碎。应该用数组传参（<code>execFile</code> 而非 <code>exec</code>）。</li>
<li><strong>并发写冲突</strong>：两个 Agent 线程同时修改同一个文件，后提交的会覆盖前者。Harness 要么加文件锁，要么把写操作串行化。</li>
<li><strong>副作用不可控</strong>：Agent 调用 <code>npm install</code> 改了 <code>node_modules</code>， Harness 如果没有快照机制，回滚时只能 <code>git checkout .</code>，代价很大。</li>
</ul>
<h2 id="上下文窗口与工具协议设计">上下文窗口与「工具协议」设计<a aria-hidden="true" tabindex="-1" href="#上下文窗口与工具协议设计"><span class="anchor-link"> #</span></a></h2>
<p>Agent 每次做决策，依赖的是 Harness 喂给它的上下文。上下文给多了浪费 token，给少了 Agent 瞎猜。Harness 的职责之一就是<strong>做信息的策展人（Curator）</strong>。</p>
<p>以代码修 bug 为例，理想的信息流应该是：</p>

<p>Harness 实现这种分层，通常依赖几种机制：</p>
<p><strong>1. 符号索引（Symbol Index）</strong>
预先构建文件 → 符号 → 引用的索引（比如用 Tree-sitter 或 LSP）。Agent 提到 <code>UserService.authenticate</code>，Harness 能快速找到定义位置和调用点，而不是让 Agent 在全仓库里 grep。</p>
<p><strong>2. 最近变更优先</strong>
Agent 刚修改过的文件、当前打开的编辑器标签页、最近的 git diff，这些「热数据」命中概率最高，应该优先注入上下文。</p>
<p><strong>3. 结构化摘要</strong>
不要把 10 MB 的日志全文塞给 Agent。Harness 可以先做一层预处理：提取报错行、去重堆栈、统计失败频率，再生成一段结构化摘要：</p>
<div class="code-block-wrapper"><div class="code-block-header"><span class="code-block-lang">json</span><button class="copy-button" data-copy-state="copy" aria-label="Copy code to clipboard" type="button" onclick="copyCode(this)"><span class="copy-button-text">Copy</span></button></div><pre><code class="hljs language-json"><span class="hljs-punctuation">{</span>

<p><strong>4. 动态上下文协议</strong>
Agent 和 Harness 可以约定一种「按需拉取」的协议。Agent 先拿到骨架，发现缺某个接口定义，再显式请求 <code>read_symbol("PaymentGateway.charge")</code>。这比一次性 dump 所有内容更可控。</p>
<p>关键是：<strong>Harness 比 Agent 更了解工程环境的结构，因此应该由 Harness 决定「什么值得看」，而不是让 Agent 自己翻仓库。</strong></p>
<h2 id="安全边界最小权限与可审计">安全边界：最小权限与可审计<a aria-hidden="true" tabindex="-1" href="#安全边界最小权限与可审计"><span class="anchor-link"> #</span></a></h2>
<p>前面提到了路径逃逸和命令注入，但 Harness 的安全设计不止于输入校验。它是一个纵深防御体系：</p>
<p><strong>1. 文件系统沙箱</strong>
最轻量的做法是用 <code>chroot</code> 或绑定挂载把 Agent 限制在项目目录。更现代的做法是在容器里跑 Harness（比如 Docker 的 rootless 模式），配合只读卷挂载。关键是<strong>默认拒绝</strong>：Agent 想写文件？先问过白名单。</p>
<p><strong>2. 命令白名单与参数校验</strong>
不要只校验命令名，还要校验参数模式。比如允许 <code>git diff</code>，但不允许 <code>git push</code>；允许 <code>npm test</code>，但不允许 <code>npm publish</code>。正则或预定义模板都可以：</p>

<p><strong>5. 回滚能力</strong>
Agent 改坏了代码怎么办？Harness 可以在每次写操作前自动 <code>git stash</code> 或打临时分支。如果 Agent 连续多步修改后整体失败，Harness 能一次性回滚到起点，而不是让用户手动 <code>git checkout</code> 20 个文件。</p>
<h2 id="小结">小结<a aria-hidden="true" tabindex="-1" href="#小结"><span class="anchor-link"> #</span></a></h2>
<p>把 AI Agent 接入工程工作流，不能只靠模型能力的提升，还需要一个可靠的 Harness 来做「安全手柄」。几个核心观点：</p>
<ol>
<li><strong>Harness 是运行时，不是协议</strong>。Function Calling / MCP 定义了 Agent 怎么表达意图，Harness 负责在真实环境里安全地执行和回传结果。</li>
<li><strong>上下文应该由 Harness 策展</strong>。Agent 不该自己翻仓库，Harness 要根据任务阶段，按需注入符号、摘要和动态数据，控制 token 消耗和信息精度。</li>
<li><strong>安全是默认拒绝 + 可审计</strong>。沙箱、白名单、网络隔离是基础，操作日志和回滚能力才是让人敢把 Agent 放进 CI 的底气。</li>
</ol>
