15:T6e5d,<h1 id="常规加解密摘要与门限算法的种类与应用">常规加解密、摘要与门限算法的种类与应用<a aria-hidden="true" tabindex="-1" href="#常规加解密摘要与门限算法的种类与应用"><span class="anchor-link"> #</span></a></h1>
<p>日常开发里，「加密」常被当成万能词：HTTPS、密码存储、文件校验、接口签名……其实背后至少几类能力——<strong>保密（加解密）</strong>、<strong>完整性（摘要）</strong>、<strong>身份与密钥分发（非对称）</strong>，以及密码机场景里常见的<strong>门限控制（秘密共享）</strong>。把种类拆开，比背一堆算法名更有用。</p>
<p>本文按摘要、对称、非对称（RSA / ECC）、门限秘密共享梳理常见算法，各从 <strong>原理</strong> 与 <strong>应用</strong> 两侧说明；末节简要带过后量子（PQC）。证书与信任链细节见此前的 <a href="/post/pkitrustarch">PKI 体系结构与证书信任链</a>。</p>
<h2 id="先分清要解决的问题">先分清要解决的问题<a aria-hidden="true" tabindex="-1" href="#先分清要解决的问题"><span class="anchor-link"> #</span></a></h2>
<table>
<thead>
<tr>
<th>目标</th>
<th>典型手段</th>
<th>一句话</th>
</tr>
</thead>
<tbody>
<tr>
<td>保密</td>
<td>对称 / 非对称加密</td>
<td>没有密钥的人读不懂明文</td>
</tr>
<tr>
<td>完整性</td>
<td>摘要（哈希）</td>
<td>内容被改过就能发现</td>
</tr>
<tr>
<td>认证 / 不可抵赖</td>
<td>签名、MAC</td>
<td>证明「谁发的」或「双方共享密钥下的消息」</td>

<tr>

<p>实务系统几乎总是<strong>组合</strong>使用：例如 TLS 用非对称做身份与握手，再用 AES 保护会话；Git / 软件包用摘要做完整性校验；密码机用门限分片管理主密钥/管理令牌。下文按算法族展开。</p>
<h2 id="摘要算法把任意长度变成固定指纹">摘要算法：把任意长度变成固定指纹<a aria-hidden="true" tabindex="-1" href="#摘要算法把任意长度变成固定指纹"><span class="anchor-link"> #</span></a></h2>
<h3 id="原理单向抗碰撞的压缩函数">原理：单向、抗碰撞的压缩函数<a aria-hidden="true" tabindex="-1" href="#原理单向抗碰撞的压缩函数"><span class="anchor-link"> #</span></a></h3>
<p>摘要（哈希）算法把任意长度输入映射成固定长度输出，例如 SHA-256 输出 256 bit。理想性质包括：</p>
<ul>
<li><strong>单向性</strong>：由摘要反推原文不可行</li>
<li><strong>抗碰撞</strong>：很难找到两段不同输入得到同一摘要</li>
<li><strong>雪崩效应</strong>：输入改一比特，输出面目全非</li>
</ul>
<p>常见成员：</p>
<table>
<thead>
<tr>
<th>算法</th>
<th>输出长度</th>
<th>现状（工程视角）</th>
</tr>
</thead>
<tbody>
<tr>
<td>MD5</td>
<td>128 bit</td>
<td>已不适合安全场景；碰撞攻击成熟</td>
</tr>
<tr>
<td>SHA-1</td>
<td>160 bit</td>
<td>已不适合新系统；浏览器/CA 早已弃用</td>
</tr>
<tr>
<td>SHA-256 / SHA-384 / SHA-512</td>
<td>256/384/512 bit</td>
<td>当前主流默认</td>
</tr>
<tr>
<td>SHA-3（如 SHA3-256）</td>
<td>可变</td>
<td>备用族；与 SHA-2 结构不同</td>
</tr>
<tr>
<td>BLAKE2 / BLAKE3</td>
<td>可变</td>
<td>性能友好，部分新协议在用</td>
</tr>
</tbody>
</table>
<p>注意：摘要<strong>不是加密</strong>。摘要结果通常可公开；它不提供保密，只提供「指纹」。需要「既完整又带密钥认证」时，用 <strong>HMAC</strong>（如 HMAC-SHA256），而不是裸哈希密码或裸哈希接口参数。</p>
<p>密码存储则常用 <strong>慢哈希 / 密钥派生</strong>：bcrypt、scrypt、Argon2、PBKDF2 等——目标是故意变慢、抗暴力，与 SHA-256 直接存密码哈希不是同一类问题。</p>
<h3 id="应用校验签名预处理密钥派生">应用：校验、签名预处理、密钥派生<a aria-hidden="true" tabindex="-1" href="#应用校验签名预处理密钥派生"><span class="anchor-link"> #</span></a></h3>
<ul>
<li><strong>完整性校验</strong>：镜像 ISO、软件包、对象存储 ETag / Content-MD5（遗留）、Git 对象 ID</li>
<li><strong>数字签名的输入</strong>：RSA / ECDSA 通常签的是消息摘要，而不是整段明文</li>
<li><strong>证书与 PKI</strong>：证书指纹、OCSP / CRL 相关标识；算法选型影响整条信任链（见 PKI 文）</li>
<li><strong>TLS / 协议</strong>：握手 transcript 的哈希、HKDF 等密钥派生</li>
<li><strong>去重与索引</strong>：内容寻址存储（CAS）用哈希当键——此处更关心唯一性与性能，安全抗碰撞要求因场景而异</li>
</ul>
<p>选型建议：新系统默认 <strong>SHA-256</strong>（或按协议要求选 SHA-384/512）；不要用 MD5/SHA-1 做安全相关校验。看到「SHA1 指纹」的遗留系统，应标为技术债并规划迁移。</p>
<h2 id="aes对称加密的主力">AES：对称加密的主力<a aria-hidden="true" tabindex="-1" href="#aes对称加密的主力"><span class="anchor-link"> #</span></a></h2>
<h3 id="原理一块共享密钥同一算法加解密">原理：一块共享密钥，同一算法加解密<a aria-hidden="true" tabindex="-1" href="#原理一块共享密钥同一算法加解密"><span class="anchor-link"> #</span></a></h3>
<p>对称加密里，加密与解密使用<strong>同一把密钥</strong>。AES（Advanced Encryption Standard）是分组密码：明文按固定块（128 bit）处理，密钥长度可选 128 / 192 / 256 bit。</p>
<p>仅有「算法」不够，还要选<strong>工作模式</strong>：</p>
<ul>
<li><strong>GCM</strong>：目前最常见的认证加密（AEAD），同时提供保密与完整性</li>
<li><strong>CBC</strong> 等：老系统仍可见，需额外 MAC，误用风险更高</li>
<li><strong>ECB</strong>：几乎只适合教学反例，相同明文块产生相同密文块</li>
</ul>
<p>安全边界很清晰：<strong>密钥保密 ≈ 安全</strong>。算法公开、实现开源都不减损安全性；真正要命的是密钥泄露、弱随机数、错误模式或明文密钥硬编码。</p>
<p>相对非对称，AES 的优势是<strong>快、适合大数据量</strong>；短板是通信双方必须先安全地共享密钥。</p>
<h3 id="应用磁盘tls-会话应用层密封">应用：磁盘、TLS 会话、应用层密封<a aria-hidden="true" tabindex="-1" href="#应用磁盘tls-会话应用层密封"><span class="anchor-link"> #</span></a></h3>
<ul>
<li><strong>全盘 / 卷加密</strong>：BitLocker、FileVault、LUKS 等底层常用 AES</li>
<li><strong>TLS 记录层</strong>：握手完成后，应用数据多由 AES-GCM（或 ChaCha20-Poly1305）保护</li>
<li><strong>应用层</strong>：数据库字段加密、对象存储服务端加密、消息中间件 payload 密封</li>
<li><strong>令牌与本地存储</strong>：部分框架用 AES 封装会话或敏感配置（仍须管好主密钥）</li>
</ul>
<p>工程上真正难的往往不是「选 AES」，而是：<strong>密钥从哪来、存哪、如何轮换、谁有权限解密</strong>。跨网络首次建立共享密钥，就轮到非对称或密钥协商协议。</p>

class="katex"><span class="katex-mathml"><math xmlns="http://www.w3.org/1998/Math/MathML"><semantics><mrow><mi>q</mi></mrow><annotation encoding="application/x-tex">q</annotation></semantics></math></span><span class="katex-html" aria-hidden="true"><span class="base"><span class="strut" style="height:0.625em;vertical-align:-0.1944em;"></span><span class="mord mathnormal" style="margin-right:0.03588em;">q</span></span></span></span> 等便于加速的参数）。</p>
<p>两条主用途不要混：</p>
<ul>
<li><strong>加密</strong>：公钥加密 → 私钥解密（常用于封装一小段对称密钥，而非直接加密大文件）</li>
<li><strong>签名</strong>：私钥签名 → 公钥验签（证明持有私钥且内容未被篡改；通常签摘要）</li>
</ul>
<p>RSA 运算是模幂，相对 AES <strong>慢一个数量级以上</strong>，密钥也更大。今日新建系统常见 <strong>2048 bit</strong> 起步，长期或高要求场景会看到 <strong>3072</strong> 及以上。直接用 RSA「加密整盘数据」既慢又不必要——标准做法是 <strong>RSA/ECC 传密钥，AES 传数据</strong>（混合加密）。</p>
<p>填充不可省：加密用 <strong>OAEP</strong>，签名用 <strong>PSS</strong>（或协议规定的方案）。裸 RSA 或陈旧 PKCS#1 v1.5 误用，是历史漏洞的温床。</p>
<h3 id="应用证书签名密钥封装">应用：证书、签名、密钥封装<a aria-hidden="true" tabindex="-1" href="#应用证书签名密钥封装"><span class="anchor-link"> #</span></a></h3>
<ul>
<li><strong>TLS / HTTPS</strong>：早期可用 RSA 做密钥交换；现代套件里 RSA 证书更多承担 <strong>签名</strong> 角色，密钥协商常交给 ECDHE</li>
<li><strong>证书与 PKI</strong>：大量服务器证、代码签名证仍是 RSA 公钥</li>
<li><strong>代码签名、文档签名、邮件 S/MIME</strong>：用私钥证明发布者身份</li>
<li><strong>JWT / JWS</strong> 等：<code>RS256</code> 一类算法即「SHA-256 + RSA 签名」</li>
</ul>
<p>常见坑：密钥过短、私钥进仓库、用同一密钥对既当加密又当签名且生命周期混乱、自定义「加密填充」。能调用系统或成熟库的高层 API，就不要自己拼模幂。</p>
<h2 id="ecc更短密钥同等强度">ECC：更短密钥、同等强度<a aria-hidden="true" tabindex="-1" href="#ecc更短密钥同等强度"><span class="anchor-link"> #</span></a></h2>
<h3 id="原理椭圆曲线离散对数">原理：椭圆曲线离散对数<a aria-hidden="true" tabindex="-1" href="#原理椭圆曲线离散对数"><span class="anchor-link"> #</span></a></h3>
<p>椭圆曲线密码（ECC）建立在曲线点群上的 <strong>离散对数问题</strong> ：已知基点 <span class="katex"><span class="katex-mathml"><math xmlns="http://www.w3.org/1998/Math/MathML"><semantics><mrow><mi>G</mi></mrow><annotation encoding="application/x-tex">G</annotation></semantics></math></span><span class="katex-html" aria-hidden="true"><span class="base"><span class="strut" style="height:0.6833em;"></span><span class="mord mathnormal">G</span></span></span></span> 与标量倍点 <span class="katex"><span class="katex-mathml"><math xmlns="http://www.w3.org/1998/Math/MathML"><semantics><mrow><mi>k</mi><mi>G</mi></mrow><annotation encoding="application/x-tex">kG</annotation></semantics></math></span><span class="katex-html" aria-hidden="true"><span class="base"><span class="strut" style="height:0.6944em;"></span><span class="mord mathnormal" style="margin-right:0.03148em;">k</span><span class="mord mathnormal">G</span></span></span></span>，反推标量 <span class="katex"><span class="katex-mathml"><math xmlns="http://www.w3.org/1998/Math/MathML"><semantics><mrow><mi>k</mi></mrow><annotation encoding="application/x-tex">k</annotation></semantics></math></span><span class="katex-html" aria-hidden="true"><span class="base"><span class="strut" style="height:0.6944em;"></span><span class="mord mathnormal" style="margin-right:0.03148em;">k</span></span></span></span> 困难。运算是点的标量乘，同等安全强度下，密钥长度远短于 RSA——例如约 <strong>256 bit</strong> 的曲线强度，粗略对标数千 bit 的 RSA。</p>
<p>常见曲线与用途（点到为止）：</p>
<ul>
<li><strong>NIST P-256</strong> 等：TLS、证书生态里很常见</li>
<li><strong>X25519</strong>：密钥协商（Diffie–Hellman 变体）</li>
<li><strong>Ed25519</strong>：签名（EdDSA），实现简洁、性能好</li>
</ul>
<p>更短的密钥意味着更小的证书、更快的握手，对移动端与高并发终止特别友好。代价是曲线与参数必须选自可信集合；「自己发明一条曲线」通常是事故预告。</p>
<h3 id="应用现代-tls-与移动端的默认选择">应用：现代 TLS 与移动端的默认选择<a aria-hidden="true" tabindex="-1" href="#应用现代-tls-与移动端的默认选择"><span class="anchor-link"> #</span></a></h3>
<ul>
<li><strong>ECDHE</strong>：TLS 中提供前向保密的密钥协商（会话密钥泄露不回溯历史流量）</li>
<li><strong>ECDSA / EdDSA</strong>：证书签名、JWT（如 <code>ES256</code>）、SSH 主机密钥与用户密钥</li>
<li><strong>与 RSA 的取舍</strong>：新系统优先 ECC（性能、体量）；仍需兼容老客户端或既有 RSA 证书链时保留 RSA</li>
</ul>
<p>证书里的「公钥算法」字段正是 RSA / ECC 等的落点；依赖方如何验证整条链，见 <a href="/post/pkitrustarch">PKI 文</a>。</p>
<h2 id="门限与秘密共享shamir-等">门限与秘密共享：Shamir 等<a aria-hidden="true" tabindex="-1" href="#门限与秘密共享shamir-等"><span class="anchor-link"> #</span></a></h2>
<p>日常说的 <strong>Shamir 秘密共享（Shamir's Secret Sharing, SSS）</strong>，由 Adi Shamir 提出。它 <strong>不是</strong> AES 那种加解密算法，也<strong>不是</strong> RSA/ECC 那种公钥算法，而是 <strong>秘密共享（Secret Sharing）</strong> 方案；带「至少 t 份才能还原」约束时，常归入更广义的 <strong>门限密码 / 门限方案（Threshold Cryptography）</strong> 一类。</p>
<p>相邻概念别混：</p>
<table>
<thead>
<tr>
<th>名称</th>
<th>解决什么</th>
</tr>
</thead>
<tbody>
<tr>
<td>秘密共享（如 Shamir）</td>
<td>把一个秘密拆成 n 份，任意 t 份可还原；少于 t 份得不到秘密</td>
</tr>
<tr>
<td>门限签名 / 门限解密</td>
<td>多把私钥分片协作完成签名或解密，完整私钥可不在单点出现</td>
</tr>
<tr>
<td>普通备份拷贝</td>
<td>每份都是完整密钥——任一泄露即全盘失守，没有门限保护</td>
</tr>
</tbody>
</table>
<h3 id="原理t-of-n-与多项式插值">原理：t-of-n 与多项式插值<a aria-hidden="true" tabindex="-1" href="#原理t-of-n-与多项式插值"><span class="anchor-link"> #</span></a></h3>
<p>Shamir 方案的直觉：在有限域上构造一条次数为 <span class="katex"><span class="katex-mathml"><math xmlns="http://www.w3.org/1998/Math/MathML"><semantics><mrow><mi>t</mi><mo>−</mo><mn>1</mn></mrow><annotation encoding="application/x-tex">t-1</annotation></semantics></math></span><span class="katex-html" aria-hidden="true"><span class="base"><span class="strut" style="height:0.6984em;vertical-align:-0.0833em;"></span><span class="mord mathnormal">t</span><span class="mspace" style="margin-right:0.2222em;"></span><span class="mbin">−</span><span class="mspace" style="margin-right:0.2222em;"></span></span><span class="base"><span class="strut" style="height:0.6444em;"></span><span class="mord">1</span></span></span></span> 的随机多项式，把秘密放在常数项（或约定的求值点）；给每人分发曲线上的一个点（份额）。任意 <strong>t</strong> 个点可唯一确定多项式从而还原秘密；<strong>少于 t 个点</strong>在信息论意义上得不到关于秘密的有效信息。</p>
<p>工程参数写作 <strong>t-of-n</strong>（或 m-of-n）：例如 3-of-5，表示发 5 份管理份额，任意 3 份可合成，2 份不行。门限同时提供：</p>
<ul>
<li><strong>抗单点作恶</strong>：一个人拿不到完整主密钥 / 管理令牌</li>
<li><strong>抗部分丢失</strong>：允许丢几份份额仍能恢复（只要还够 t 份）</li>
</ul>
<p>份额本身仍须按敏感物料保管（分人、分地、分介质）；算法只保证「不够门限合不成」，不代替物理与流程控制。</p>
<h3 id="应用密码机管理与密钥仪式">应用：密码机管理与密钥仪式<a aria-hidden="true" tabindex="-1" href="#应用密码机管理与密钥仪式"><span class="anchor-link"> #</span></a></h3>
<p>最典型的是 <strong>HSM / 密码机</strong> 与高保障密钥管理：</p>
<ul>
<li><strong>门限 token / 管理卡分发</strong>：设备初始化或密钥仪式（key ceremony）时，把主密钥、解封密钥或管理员权限拆成多份智能卡 / token，发给多名管理员；开机、解封、关键运维需凑齐门限</li>
<li><strong>根密钥与 CA 仪式</strong>：根私钥或种子不由单人持有，降低内部威胁与单人失误面</li>
<li><strong>系统解封</strong>：例如部分密钥管理系统用 Shamir 拆分 master key，集群启动需多位运维共同解封</li>
</ul>
<p>与 AES/RSA 的关系：门限方案管的是 <strong>「谁有权拼出那把关键钥匙」</strong> ；拼出之后，真正加密业务数据的往往仍是 AES，签名仍可能是 RSA/ECC。密码机里常见组合是：<strong>业务密钥在机内</strong>，<strong>管理权限用门限 token 控制出机/解封/双人复核</strong>。</p>
<h2 id="pqc面向量子时代的算法族">PQC：面向量子时代的算法族<a aria-hidden="true" tabindex="-1" href="#pqc面向量子时代的算法族"><span class="anchor-link"> #</span></a></h2>
<h3 id="原理换一套难解问题">原理：换一套「难解问题」<a aria-hidden="true" tabindex="-1" href="#原理换一套难解问题"><span class="anchor-link"> #</span></a></h3>
<p>若大规模容错量子计算机可用，Shor 算法将严重威胁 <strong>RSA 与 ECC</strong> 所依赖的数学问题。对称算法与哈希相对更稳：主要对策是 <strong>加长密钥 / 输出</strong>（例如 AES-256、更长摘要），而非整体换族。</p>
<p>后量子密码（PQC）改用被认为抗量子的问题（格、哈希签名等）。NIST 已推进标准化，工程上常听到的方向包括：</p>
<ul>
<li><strong>ML-KEM</strong>（Kyber）：密钥封装（KEM），用于协商/封装对称密钥</li>
<li><strong>ML-DSA</strong>（Dilithium）等：数字签名</li>
</ul>
<p>过渡期常见 <strong>混合模式</strong>：经典算法（如 X25519）与 PQC KEM 并行，两者都破才危及会话——降低「标准未稳就单押一家」的风险。</p>
<h3 id="应用标准落地与迁移现实">应用：标准落地与迁移现实<a aria-hidden="true" tabindex="-1" href="#应用标准落地与迁移现实"><span class="anchor-link"> #</span></a></h3>
<ul>
<li><strong>TLS / 证书</strong>：浏览器与部分 CDN、云厂商已在试验或灰度混合密钥交换；证书侧 PQC 签名与双证书链条仍在演进</li>
<li><strong>工程代价</strong>：公钥与密文往往更大，握手体积与 CPU 上升；协议、硬件、HSM、合规清单都要跟着改</li>
<li><strong>务实判断</strong>：存档期很长的机密（「现在截获、将来解密」）应优先评估；一般 Web 业务跟主流协议与供应商路线即可，不必自行实现 PQC 原语</li>
</ul>
<p>PQC 是<strong>长期迁移题</strong>，不是明天把 RSA 全局替换的开关。先把摘要弃用 MD5/SHA-1、对称用 AEAD、非对称密钥长度与填充做对，收益更确定。</p>

<p>典型流水线可以记成一句：</p>
<p><strong>摘要保真 → 非对称认人 / 传钥匙 → 对称护航大数据；关键主密钥可用门限分片托管。</strong></p>
<p>例如 TLS：证书（RSA/ECC 公钥 + 签名）证明服务器身份 → ECDHE（或混合 PQC）协商会话密钥 → AES-GCM 加密应用数据；全程多次用到 SHA 族哈希。密码机侧则另有一条管理链：Shamir 门限 token → 解封/授权 → 机内再用对称或非对称做业务运算。</p>
<h2 id="小结">小结<a aria-hidden="true" tabindex="-1" href="#小结"><span class="anchor-link"> #</span></a></h2>
<ol>
<li><strong>摘要</strong>解决「有没有被改过」；<strong>对称加密</strong>解决「大量数据怎么保密」；<strong>非对称</strong>解决「钥匙怎么分、身份怎么证」；<strong>门限秘密共享</strong>（如 Shamir）解决「不能让单人独掌完整秘密」。</li>
<li>新系统默认组合大致是：SHA-256（或协议指定）、AES-GCM、ECC（协商/签名）；RSA 多出现在兼容与存量证书；HSM/密码机管理常见 t-of-n 分片。</li>
<li><strong>PQC</strong> 值得跟踪，但优先把经典算法用对：弃用 MD5/SHA-1、AEAD、足够的密钥长度与正确填充。</li>
